# herdr vs agent-session-host: study

Status: research note, 2026-10-05. Read-only study: herdr was not installed or run. Sources: `herdr/` (v0.9.3, `herdr/Cargo.toml:3`) and `ash/` (spec DRAFT v0.3 plus `ash/PR11.diff`, Architecture v1).

Path shorthands used below:
- `hd/` = `herdr/docs/next/website/src/content/docs/` (the docs for the current version)
- `hs/` = `herdr/src/`
- `sh.md` = `ash/spec/session-host.md`
- `PR11:N` = line N of `ash/PR11.diff`. Architecture v1 starts at `PR11:618`: §A1 `:626`, §A2 `:645`, §A3 `:659`, §A4 `:705`, §A5 `:762`, §A7 `:813`, §A8 `:835`, §A10 `:886`, §A11 `:909`.

**Short answer.** herdr is a tmux replacement built for agents: one server per user holds every PTY, and it adds screen-based working/blocked/idle detection, a JSON socket API and CLI, and restore of the layout plus `--resume` after a restart. It covers our *terminal and observation* pains well. It does not cover the parts agent-session-host exists for: per-session holders that survive a host restart, authenticated or least-privilege control, goals, park, a durable doorbell queue, a journal, or structured Codex/Muse surfaces. Its socket has the same property ash rejects tmux for. **Recommendation: (c), borrow ideas.** As a separate owner decision, herdr could be a short-term replacement for raw tmux in today's swarm.

## 1. What herdr is

| Topic | Finding | Evidence |
| --- | --- | --- |
| Shape | One Rust binary that runs as a background **server** with one or more TUI **clients**. The server owns every pane's PTY and process. `herdr server` runs it headless "for supervised or service-style setups". Named sessions are separate servers, each with its own socket and state. | `hd/concepts.mdx` (Session; Client and server); `hd/cli-reference.mdx:124-133` |
| Pane model | Workspace → tab → pane. A pane is a real terminal. An "agent" is the recognized process inside a pane. Agents are addressed by pane id (`w1:p2`) or by a unique live name `[a-z][a-z0-9_-]{0,31}`, which is cleared when the agent exits. | `hd/concepts.mdx`; `hd/agent-automation.mdx` (Agent identity and launch) |
| Detach | The client detaches (`ctrl+b q`) while the server and its processes keep running. This is the strongest persistence path. | `hd/session-state.mdx:8-22` |
| Server restart / reboot | **Processes do not survive.** The layout (workspaces, tabs, panes, cwd, focus) is restored from `session.json`. Panes come back as fresh shells unless a native agent session reference exists. Pane screen history is opt-in and off by default because of secrets (`[experimental] pane_history`). The server keeps 48 rotating layout snapshots and failed-load backups, and never restores them automatically. | `hd/session-state.mdx:8-70` |
| "Resume supported agent sessions" | Integrations (Claude via a `SessionStart` hook) report a native session id. After a restart the pane runs e.g. `claude --resume <id>` or `codex resume <id>`. The command is built from the bare executable and the id only: `hs/agent_resume.rs:204-206` and the test at `:464` expect `["claude","--resume","claude-session"]`, so the original model, permission and MCP flags are not carried. Self-reporting agents can supply their own `resume_argv`, but its first word must be a plain command on `PATH`, not a path. Restored agents start one at a time, 100 ms apart. **Resume starts only after a client attaches and reports its size and theme.** A headless server after reboot leaves agents un-resumed until someone attaches. | `hd/session-state.mdx:73-110` (`:86`); `hd/add-herdr-support.mdx` (Report the resume command); `hs/app/agent_resume.rs:99-103` (no candidates while the terminal area is 0×0); `hs/server/headless.rs:694-700`; `herdr/CHANGELOG.md` 0.9.2 |
| Live handoff | An experimental, opt-in `herdr update --handoff` passes the PTY file descriptors to a new server (SCM_RIGHTS, in batches). In-flight waits and subscriptions are dropped. It is only available for installs made by herdr's own updater, not Homebrew. | `hd/session-state.mdx:117-136`; `hs/server/handoff.rs:25,179,381` |
| State detection | (1) Herdr finds the agent's foreground process. (2) It matches the live **bottom of the buffer** (not the user's viewport) against per-agent TOML **manifests** that use AND/OR/NOT rules, regions and priorities. (3) PTY activity is the main signal for `working`. (4) Hook or plugin reports (`pane.report_agent` with a monotonic `seq`) override the screen for Pi, OMP, OpenCode and a few others. **Claude state comes only from the screen**, and Codex from turn hooks plus screen blockers. `blocked` is strict: it needs a known approval or question UI. If no rule matches, the state **falls back to `idle`**. `agent explain` shows which rule matched. Manifests auto-update from herdr.dev unless `[update] manifest_check=false`, and local overrides live in `~/.config/herdr/agent-detection/`. | `hs/detect/mod.rs:1-37`; `hs/detect/manifests/claude.toml:79-215`; `hd/agents.mdx:64-105`; `hd/integrations.mdx:62,112`; `herdr/AGENTS.md` (Screen detection is evidence-based) |
| Dialogs relevant to us | Folder-trust rules exist for Codex (`codex.toml:35-50`), Muse (`muse.toml:18-36`) and Qwen. **A Claude folder-trust rule: not found.** Claude permission, MCP and form prompts are covered (`claude.toml:80-215`). **A usage-limit or rate-limit rule for any agent: not found** (a grep for "usage limit" or "rate limit" in the manifests matches nothing). Herdr only *detects* blocking dialogs and never answers them. | grep of `hs/detect/manifests/` |
| Socket API and CLI | Line-delimited JSON over a Unix socket (`~/.config/herdr/herdr.sock`) or a Windows named pipe, with a JSON Schema available through `herdr api schema`. Agents can create workspaces, tabs and splits; `pane run`, `send-text`, `send-keys`, `read` and `wait-output`; `agent start --kind claude\|codex\|muse…`; `agent prompt` (bracketed paste plus Enter, refused with `agent_blocked` when the agent is blocked, optional atomic `--wait`); `agent wait --until blocked\|idle\|done` (server-owned, pinned to the pane's occupant, no default timeout); `events.subscribe` (with an `events_lost` signal, then snapshot reconciliation); `session.snapshot`; `server.stop`. Every pane process receives `HERDR_SOCKET_PATH`, `HERDR_PANE_ID` and related variables. | `hd/socket-api.mdx:36-115,245-256,630-650`; `hd/agent-automation.mdx:60-85` |
| Delivery semantics | No queue and no turn awareness: "It does not track individual turns". A timeout "does not prove that no input was sent", so the caller must read before retrying. | `hd/agent-automation.mdx:72-82` |
| Remote machines | SSH only. Each machine runs its own server, and the client shows them together. `herdr --machine <label> agent prompt …` forwards CLI commands over SSH, with a shared ControlMaster. | `hd/connecting-machines.mdx`; `hd/cli-reference.mdx:53-76` |
| Plugins | A manifest (`herdr-plugin.toml`) declares actions, event hooks, panes and startup commands. "The entire Herdr CLI is the plugin API". Plugins are not reviewed or sandboxed and run as the user. | `hd/plugins.mdx:1-50` |
| Security model | Unix: the socket is bound and **then** chmodded to 0600 (`hs/api/server.rs:89-90`; `hs/server/socket_paths.rs:11,73`), which leaves a race between listen and chmod. The parent directory is made with `create_dir_all` (`hs/ipc.rs:83-89`), with no explicit 0700 found. **No token, no peer-credential check and no per-caller scopes: not found.** Any process of the same UID, including every agent in a pane (which receives `HERDR_SOCKET_PATH`), can read, type into, prompt or close any pane, report a false state for any pane id, or stop the server. On Windows the pipe DACL is owner plus SYSTEM (`hs/ipc.rs:138-163`), and the docs explicitly trust all same-account processes (`hd/windows-beta.mdx:52`). | as cited |
| License, stack, cadence | Apache-2.0 (`herdr/LICENSE`). Rust, with an embedded libghostty VT (`herdr/crates/ghostty-vt`). 59 releases from 0.1.0 (2026-03-27) to 0.9.3 (2026-09-29), about 2 per week, with 9 "Breaking Changes" sections; for example 0.9.2 removed `pane.graphics.*`. Still pre-1.0. | `herdr/CHANGELOG.md` |

## 2. herdr against agent-session-host's responsibilities

| ash responsibility (source) | herdr | Evidence and gap |
| --- | --- | --- |
| **Supervisor**: registry, admission, scheduling, journal, reconciliation, one per OS security domain (§A2 `PR11:645-657`; `sh.md` §5) | **Partial** | The herdr server is one per user or session and supervises panes. It has no admission or scheduling, no goal awareness, and no reconciliation of durable session records beyond the layout. A crashed agent leaves a shell, and herdr does not restart it. |
| **Holder**: one per execution, outlives the supervisor, authenticated writes with epoch, generation and lease (§A2; `sh.md` §5, §14) | **Missing** | All PTYs live in the single server process, which is the same failure mode as `tb-sessiond` today (`sh.md` §2.7). Survival across replacement is only through the experimental handoff (`hd/session-state.mdx:117`). There is no per-pane holder and no write authentication. |
| **Registry** (`sh.md` §5, §12.1 `list/show`) | **Covered (terminal level)** | `agent list`, `pane list`, `session.snapshot`, `session list --json` and the sidebar give live state, cwd and agent kind. The registry has no process, role, board, goal or harness-version fields. Custom tokens via `pane.report_metadata` could carry labels (`hd/socket-api.mdx` metadata section). |
| **Control API** with peer creds, capability tokens and the supervision matrix (`sh.md` §6; §A3 gate `PR11:659-704`) | **Partial (API) / Missing (auth)** | It has a rich JSON API and schema. Authentication is only the socket mode (see §1, Security model). Nothing like §6.2 tokens, the §6.3 matrix or the §A3 signed-ingress gate exists. |
| **Park / restart / reboot** (`sh.md` §8, §11; §A7 `PR11:813-834`) | **Partial** | It has restart-and-resume of layout and native session. It has no park note, no `handoff_ref`, no drain or admission close, and no restart report. It does not start at login (a launchd/LaunchAgent mention: not found in `hs/` or `hd/`). Resume waits for a client (§1). Resume drops the launch flags, which conflicts with §A7 "flags are never reconstructed" and §A8 "resolve by hash, never by PATH" (`PR11:827,839`). |
| **Harness adapters** (Claude PTY, Codex app-server, Muse `muse serve`; §A4 `PR11:705-761`) | **Partial (PTY/preserve only)** | Twenty-plus agents are supported through the TUI and screen manifests, and Muse is detected (`muse.toml`), but Muse is absent from the native-resume table (`hd/session-state.mdx:88-108`). There is no structured surface: Codex runs as a TUI, not through app-server `turn/steer`, and there is no Claude stream-json and no MSP. This covers §A4's "Preserve" row only, and only partly (its readiness signal is the manifest). |
| **Goal / notice delivery, doorbell modes** (`sh.md` §2.4-2.5, §7) | **Partial** | `agent prompt` is a `next_turn`-ish paste with a refusal when blocked, and `agent wait` covers readiness. There is no durable inbox, coalescing, goal-revision ack, `steer` or `interrupt` lane, or delivery receipts. `outcome_unknown` is explicitly the caller's problem (`hd/agent-automation.mdx:82`). |
| **Events / journal** (R6 `sh.md` §4; §A5 `PR11:762-790`) | **Partial** | It has an event stream with state changes and an explicit `events_lost` signal. Events are not persisted, there is no hash-chained audit, and there are no turn or goal or limit events. |
| **Attach / watch** (`sh.md` §12) | **Covered (human)** | It has a multi-client TUI and `agent attach [--takeover]` (`hd/cli-reference.mdx:347`). A read-only watch mode: not found. |
| **Remote / transport** (`sh.md` §13) | **Partial** | SSH saved machines and `--machine` forwarding. Transport is fixed to SSH. |

## 3. herdr against our pains

| Pain | Verdict | Why |
| --- | --- | --- |
| Re-arming the doorbell by hand | **Partial** | herdr has no Matrix or `a2a` integration. A small outside loop could replace the in-session `a2a wait`: `a2a wait` → `herdr agent wait <pane> --until idle --until done` → `herdr agent prompt <pane> "<notice>"`. The doorbell then lives outside the session and never needs re-arming. Delivery stays a PTY paste with no receipt (`hd/agent-automation.mdx:72-82`). |
| Sessions stuck on prompts (usage limit, folder trust) | **Partial / risky** | `agent wait --until blocked` and events make stuck panes visible, and Codex and Muse trust dialogs are rules. A Claude trust rule and any usage-limit rule: **not found**. An unmatched screen falls back to **`idle`** (`hd/agents.mdx:76`), so a usage-limit dialog may look idle. Rules could be added as local overrides. Herdr never answers dialogs, so a supervisor would still need `agent send-keys`. |
| Restart or reboot needs manual tmux respawn plus resume | **Partial** | The layout comes back and Claude and Codex resume by id. It has no login autostart, resume waits for an attached client, resumed sessions lose launch flags, and processes still die on a server restart unless handoff works. |
| No registry of what runs where | **Covered for one machine; partial across two** | `agent list` / `session.snapshot` per server. Two Macs need saved machines over SSH and `--machine` per command. There is no merged API-level registry; the merged list is in the TUI only (`hd/connecting-machines.mdx`). |
| No machine-readable blocked/idle/working | **Covered** | This is herdr's core feature: `agent get/list` JSON, `pane.agent_status_changed` events and `agent explain`. Accuracy depends on the manifests, and Claude relies on the screen only. |

## 4. Integration options

| Option | Fit | Main reasons |
| --- | --- | --- |
| **(a) Replace agent-session-host** | Poor | It lacks holders, auth, goals, park, journal, structured adapters and admission (§2). We would rebuild all of ash on top of a same-UID open socket, and that contradicts decided §A1-§A4 points. |
| **(b) herdr as the PTY layer under ash** | Poor | (1) herdr is one process holding all PTYs, not the per-execution holder of §A2, so a host restart still kills sessions. (2) The socket gives every pane full control of every other pane, which is exactly the reason for "Never tmux: its socket gives any reachable caller broad terminal control" (`PR11:728`), *decided*. (3) Pane processes are launched by herdr (`PATH` executables, herdr-managed env), not from ash's exact finalized plan and hash-resolved build (§A8, §A9 `PR11:839,857`). (4) Rust and a fast-moving pre-1.0 API under a Go host means two release trains, and breaking changes land in minor versions. (5) It auto-fetches detection rules from herdr.dev (`hd/agents.mdx:82`), which is a remote input into readiness decisions. |
| **(c) Borrow ideas** | **Recommended** | It is Apache-2.0, so ideas, and even the TOML rule *data* with attribution, can be reused. The useful ideas are listed below. |
| **(d) Ignore** | Wasteful | herdr has solved the hardest preserve-mode problem: reliable screen readiness and blocked detection across harness versions. That is exactly A4's open qualification item (`PR11:715,725`). |

**Ideas worth borrowing (for ash):**
1. **An evidence-based detection manifest** for the preserve/PTY adapter: bottom-buffer regions, AND/OR/NOT gates, priorities, `visible_blocker`, an `explain` trace, and local overrides (`hs/detect/manifests/*.toml`; `herdr/AGENTS.md`). This gives ash's prompt-readiness qualification a concrete grammar. We should **not** copy the fallback to `idle`; ash should return `unknown` and park (§A4 "no blind Enter").
2. **A refuse-when-blocked prompt plus an atomic prompt-and-wait, pinned to the pane occupant** (`hd/socket-api.mdx:114`). This fits the Claude PTY `next_turn` path.
3. **A self-report protocol** through env vars (`HERDR_PANE_ID`, `HERDR_BIN_PATH`) with monotonic `seq`, plus release-on-exit and a safety-net clear when an idle shell is seen (`hd/add-herdr-support.mdx`). This could serve as the adapter hook contract for agy and Pi. In ash it must sit behind capability tokens.
4. **Subscription semantics**: explicit `events_lost`, then resubscribe plus snapshot reconciliation with no fake replay (`hd/socket-api.mdx` "Event subscriptions"). This matches §A5's "explicit gap or reset".
5. **Restore hygiene**: a staggered restart (`startup_per_agent_delay_ms`); failed restores stay visible with an error instead of vanishing; rotated snapshots plus failed-load backups (`hd/session-state.mdx:29-56`). These support §A7 "no session disappears silently".
6. **FD handoff in batches** (`hs/server/handoff.rs`): prior art for the re-adoption research in A-Q5. Handoff alone does not authenticate the new supervisor.
7. **Env hygiene**: new panes do not inherit the parent terminal's or Claude's session markers (`herdr/CHANGELOG.md` 0.9.2). This confirms `sh.md` §2.3.

**Separate, tactical, and outside ash:** the owner *may* pilot herdr instead of raw tmux on the two Macs while ash is being built. It would give a registry and machine-readable state now, and the doorbell loop in §3. It is no worse than tmux on security (both are same-UID), but it is also no better. It should be time-boxed, with manifest auto-update off and no third-party plugins, and none of it should become an ash dependency.

**Risks:**

| Risk | Detail |
| --- | --- |
| Maturity and cadence | It is 6 months old, pre-1.0, ~2 releases per week, and has breaking API changes in minor versions (`CHANGELOG.md`). Live handoff is experimental. |
| Rust vs Go | The host and adapters are Go (`sh.md` §3.3 "in-process Go implementations"). Embedding is not possible, so we would depend on it through a process plus socket, with a vendored-fork burden. |
| License | Apache-2.0 is compatible. Keep NOTICE and attribution if rule files are copied. Unlike HAPI (AGPL, rejected in §A10 `PR11:907`), there is no licence block. |
| Socket security | Any same-UID process controls everything (§1). There is a listen→chmod window. Any pane can spoof `report-agent` for another pane's id. This is incompatible with the `sh.md` §6.3 matrix, where agents never attach and only touch their own subtree. |
| macOS specifics | Socket path under `~/.config/herdr` (Darwin's 104-byte `sun_path` limit; short-path fallbacks exist for SSH and remote-bridge sockets, `hs/platform/unix_common.rs:280-350`; a fallback for the main API socket: not found). No launchd integration found, while ash plans a LaunchAgent for `keeper up` (`sh.md` §11). The logind shutdown save is Linux-only, so a macOS reboot relies on the periodic autosave (`hd/session-state.mdx:45`). Resume needs an attached client and its theme, so a headless login restore does not resume agents. |
| Detection drift | Claude depends on the screen only, and the manifests update remotely. A Claude UI change could misreport state until rules ship. |

## 5. Questions for the owner and Ivan's review

1. **Owner**: is the near-term need *today's tmux swarm* (registry, state, doorbell loop) or only the ash target? If it is today's swarm, do you want a time-boxed herdr pilot on one Mac, accepting same-UID control equal to tmux, or does the "Never tmux" reasoning (`PR11:728`) rule out every unauthenticated multiplexer socket?
2. **Ivan**: should §A4's "Never tmux" be widened into a general rule, "no backend whose control socket lacks per-caller authorization", so that herdr, zellij and similar tools are covered explicitly, and §13's backend table gets updated?
3. **Ivan**: for preserve-mode readiness (`PR11:715,725`), should ash adopt a herdr-style TOML rule grammar, possibly seeded from herdr's Apache-2.0 manifests, with `unknown→park` instead of `idle` fallback? Who maintains the rules per harness version alongside the §A8 probes?
4. **Owner**: for the usage-limit and folder-trust dialogs, what is the wanted policy: auto-answer (with which keys, and for which harness), park with a reason, or notify a person? herdr only detects, and has no rule for Claude's trust or any usage-limit dialog.
5. **Ivan / Alexey**: is any component allowed to take *remotely updated* behaviour rules (herdr fetches detection manifests from herdr.dev by default), or must every rule set be pinned and admitted like harness builds under §A8's known-bad and probe policy?
