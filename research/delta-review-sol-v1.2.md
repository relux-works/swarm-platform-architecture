# VISION v1.2 delta review

Reviewer role: cross-provider, adversarial architecture reviewer. Reviewed the supplied snapshot on 2026-10-05: VISION §0 and the remaining prose, all seven contracts, the owner decision sheet, the illustrative Playbook, C4 DSL and exports, all nine sequences and fourteen PNGs, against the previous joint review, the tb-keeper/ivan-curator reviews, and the three R191 diffs. Citations are current repository file lines; R191 citations are local **diff** lines, not upstream file lines.

v1.2 substantially improves the proposal, but is not ready for contract freeze. The new schemas and transactions still permit ambiguous recovery and authority decisions, and some diagrams contradict their contracts. A declared deferral that refuses an unsupported capability counts as a resolution; a proposed check is not evidence that the check already runs. Owner recommendations remain proposals, as `vision/DECISIONS-FOR-OWNERS.md:3` explicitly says. This review does not require implementing the platform in this documentation repository.

## 4. New issues in the v1.2 mechanisms

The following IDs identify defects in the newly specified contracts. Recurring old diagram fall-through and confidentiality problems are reported above under their original IDs rather than counted again as new findings.

### D-B1 — Blocker: native write precedes the durable dispatch reservation

**Evidence:** `vision/contracts/admission-and-delivery.md:78,83–86`; `diagrams/plantuml/sequence/matrix-message-injection.puml:48–51`.

The dispatcher writes the input and only then records `dispatched`. A crash after the harness accepts the write but before that record leaves a durable `queued` item, not an `unknown` item. Recovery reconciles only records between dispatched/applied, so it can resend an applied user turn or approval. The new state machine does not cover the very crash window it claims to solve.

**Required change:** persist/fsync a dispatch attempt containing the input marker, target execution/generation, controller epoch and lease before any native write. Every incomplete attempt, including crash-before-write, is uncertain until native evidence resolves it. Make final holder validation atomic with the write and prevent automatic replay of unresolved approvals/control. Qualify crashes on both sides of the write and both sides of each fsync.

### D-B2 — Blocker: idempotency commits only content, not the signed action

**Evidence:** `vision/contracts/admission-and-delivery.md:20–27,33,73–77`; compare `r191/agent-session-bridge-PR1.diff:670,673,676,704–706`.

`(principal,id)` claims bind only `body_sha256`; same-body duplicates return the existing receipt. Reusing an ID with another target, action, execution, expiry or grants is therefore accepted as a duplicate despite different signed command bytes. The host key includes the logical target but still omits action/execution and the rest of the envelope. This can return another action's success evidence or suppress a critical control action. A reference body's resolved-byte/hash check is also not stated. `origin` is retained but has no independent stable cross-carrier/derivative claim.

**Required change:** bind a stable authenticated application principal/origin ID to the complete canonical command digest; reject any changed signed scope under that identity. Use that commitment at host enqueue and on receipts, while allowing a carrier-only wrapper to vary outside it. Define key-rotation continuity and principal binding to the verified signer, not a plugin's claim. Hash/authorize immutable referenced content before dispatch. Test same body/different action, target, execution and expiry, plus cross-carrier derivatives.

### D-B3 — Blocker: update lock and ordinary closure are collapsed

**Evidence:** `vision/contracts/restart-and-takeover.md:15–21,65`; compare `r191/agent-session-host-PR11.diff:821,849`.

The new fence is one enum `open | closed | update_lock`, so it cannot represent the independent maintenance lock and ordinary operation closure together. Replacing `update_lock` with `closed` would erase the maintenance protection; retaining it leaves the restart closure/op_id without an independent record. Although agents are explicitly forbidden to clear update locks, no operator-clear transition specifies how to preserve ordinary closure. The maintenance sequence also says reconcile then release, although `update_lock` prohibits every consumer start needed for native reconciliation. New logical sessions need a host-wide maintenance gate; per-session records alone cannot fence a concurrent new intake.

**Required change:** retain a durable node/domain update lock separately from per-session ordinary fences/op_ids. Ordinary operations must never clear or replace it. Specify the operator's eligible-restore point for clearing only the update lock while all affected session closures remain, and require every new start/intake/retry/probe to test it. Persist reboot closure before steps 5–9. Add restart-vs-maintenance and new-session-during-swap traces.

### D-B4 — Blocker: the Playbook labels the classes that select kernel protection

**Evidence:** `vision/contracts/kernel-guards.md:20–29,37–44,64`; `vision/flows/swarm-project.Playbook.json:85–91`.

The Playbook chooses `kernel_class`, and narrow checks protect paths to the declared integration/success classes. K8 rejects missing/ambiguous mappings, not false mappings. A flow can label a terminal-success state `work` (or `terminal_other`) and thereby avoid the success-path CR/review checks. A migration can similarly reclassify a populated state while keeping every state singly mapped. There is no specified kernel rule binding terminal flags, completion semantics, CR ownership and transition effects to those classes. Moving the gate below B2 does not help if B2 supplies the gate's unchecked classification.

**Required change:** let kernel/domain semantics determine protected effects and accepted completion, or enforce an immutable correspondence between state flags/effects and required classes, including migrations. A state rename/relabel cannot remove review/CR predicates or redefine what consumers recognize as completion. Add relabeled-terminal, `terminal:true`/`work`, reclassification and terminal-other completion negatives at load and runtime.

### D-M1 — Major: takeover is routed through native-resume eligibility and the old plan

**Evidence:** `vision/contracts/restart-and-takeover.md:31–43,50,61`; `vision/contracts/handoff-package.md:25–26,62–65`; `diagrams/plantuml/sequence/context-takeover.puml:31–46`.

A takeover intentionally changes profile/runtime, yet it runs the same comparison that refuses any pin/posture difference and then execs the stored source plan. Rebuild's required new composition is absent from that sequence. Seed checks also say reauthorize “every pin” without distinguishing source-evidence pins from the authorized destination pin. Either legitimate takeover always refuses or a permitted branch launches the old profile while reporting the new recipient.

**Required change:** split native resume from explicitly authorized rebuild before eligibility. For rebuild, compose/admit a new destination request and plan under the closed fence; retain source pins as provenance, bind destination pins/audience separately, and refuse unsupported conversions. Keep source-plan replay exclusively on native resume.

### D-M2 — Major: board goal creation, launch and park revisions do not form a coherent transaction

**Evidence:** `vision/contracts/launch.md:29,57`; `vision/contracts/goals.md:24–29`; `vision/contracts/handoff-package.md:28,64`; `vision/contracts/restart-and-takeover.md:29`; `diagrams/plantuml/sequence/board-transition-spawn.puml:35,45–50`; `diagrams/plantuml/sequence/controlled-restart.puml:39–42`.

The worker request sends a board revision reference although LaunchRequest only defines a text goal. The worker is ready before that revision is created/published. A crash after the intent is marked done but before goal publication leaves a live worker with no authoritative board goal. Launch-time `goal.set` can also create a second launcher-owned goal. During park, the package captures the old goal reference, then B1 commits a new revision carrying its `handoff_ref`; import requires the current revision, so the just-created package can be stale immediately.

**Required change:** define a typed board-goal reference distinct from board-free text. Durably reserve/publish the exact revision as a recoverable action before ready, bind run/slot/execution, and mark the intent complete only when acknowledged. Define how a handoff references the committed park revision without a revision/digest/reference cycle, and how older immutable source-goal evidence differs from the live delivery revision.

### D-M3 — Major: a request ID alone does not make launch/reconciliation idempotent

**Evidence:** `vision/contracts/launch.md:15,48–60`; `vision/contracts/kernel-guards.md:62–63`; `diagrams/plantuml/sequence/board-transition-spawn.puml:40,47`.

The new contracts say same key/same request returns the result, but define no caller scope, changed-request conflict, durable prepare/start reservation, retention, in-progress/unknown result or controller takeover. A crash after native start but before durable registration can make `list(request_id)` empty; reissuing the key can create another writer. Another caller reusing the key could retrieve unrelated result metadata. The recovery instruction assumes the missing transactional guarantee.

**Required change:** durably bind authenticated caller/namespace + request key to an immutable resolved request digest and lifecycle reservation before start, attach execution custody to it, and reconcile uncertain starts before retry. Different bytes conflict; unauthorized callers cannot see the cached result. Retain terminal outcomes across supported recovery and compensate leases for every refusal/cancellation.

### D-M4 — Major: goal/board plugins have no admitted wire operations

**Evidence:** `vision/VISION.md:72,132,176,261`; `vision/contracts/plugins-and-interactions.md:3,8–14`; `vision/contracts/goals.md:13,24–26`; `vision/DECISIONS-FOR-OWNERS.md:38`.

The ABI is described as carrier-only, yet includes goal and B5 clients. VISION's plugin-to-host vocabulary is `manifest/envelope/cursor/health/secret.resolve`; the handshake adds `hello` and plugin receipts are mentioned separately. None defines request/response frames for `goal.get`, `goal.delivery_update`, publish/outcome acknowledgments or ledger queries. Envelope actions cannot express the read/update methods. Saying “through M3” fixes the route but not the protocol or the board principal/grant attached to each call.

**Required change:** choose an explicit typed integration RPC or a versioned admitted plugin extension, with request/result/error schemas, caller/handle scopes, correlation and replay semantics. Distinguish carrier principal evidence from the host/board/agent ledger authority. Align both ABI vocabularies and C4 B5's external-process connection; do not infer private stdin access or store access.

### D-M5 — Major: default egress changed to unrestricted assistant text, with no release transaction

**Evidence:** `vision/contracts/admission-and-delivery.md:103–105`; `diagrams/plantuml/sequence/matrix-message-injection.puml:64–70`; compare `r191/agent-session-host-PR11.diff:768–773` and `r191/agent-session-bridge-PR1.diff:777–784`.

`final_text` means the assistant's turn text, not a deterministic typed status/decision projection. It can quote private tool results or credentials even though tool events require a transcript grant. The contract specifies neither per-item sensitivity/source authorization nor durable journal-to-outbox ownership, immutable carrier-visible proposal identity, dispatch-time revocation/audience checks or uncertain-send recovery. ### D-M6 — Major: initialization forbids the input it requires, and closure lacks a scoped exception

**Required change:** define a closed-fence, operation-owned initialization/park control lane with exact typed actions, grants, destination generation, readiness and receipts. ### D-M7 — Major: the remote intent drops the authorized launch request

### D-M8 — Major: capacity gates consume an unrepresented job classification

**Evidence:** `vision/contracts/launch.md:13–32,64–74`; `diagrams/plantuml/sequence/worker-start.puml:32`; `diagrams/plantuml/sequence/remote-worker-start.puml:23`.
