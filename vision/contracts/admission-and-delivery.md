# Contract: envelopes, host-enforced admission and durable delivery

Status: VISION v1.2 contract draft (2026-10-05). Fixes A-B1 and A-B3 of `research/joint-review-sol-2026-10-05.md` (JR) and tb-keeper condition 4 (`research/pr1-reviews-2026-10-05.md`, TBK-R). It is a draft for the joint review, not a delivered schema. Where the R191 package (B) already has the rule, this contract adopts it: H:659–701 and C:643,669–684,698–708,734–773,823–834,900.

Updated 2026-10-13: accepted architecture-review findings (2026-10-13), aligned to the canonical module contracts; no implementation or activation is claimed.

## 1. Principles

1. **Provenance comes from the authenticated caller and binding, never from the payload.** A carrier's `sender` claim is kept as data (`claimed_sender`) and has no authority.
2. **Exact bytes.** An envelope is immutable after issue. Signatures cover canonical bytes (RFC 8785 JCS). Any rewrap by a carrier keeps the original bytes and `origin` ids.
3. **Three separate things:** transport admission (the data may enter the bridge), instruction authority (the data may act as a user turn), and effect authority (the action may change a session, a binding, a goal or a native dialog). An envelope gets each only by its own check.
4. **The host enforces.** The bridge's trust gate is a first filter. The session host re-checks admission at every typed mutation (§4) before it writes to a session, a goal ledger, a binding or a holder. Framing text is supplementary, never the control.
5. **Unsigned bodies do not reach stdin by default** (D-R2, adopting B's default): they become metadata-only doorbells.

## 2. Envelope `swarm-envelope/2`

Signed part (canonical JSON; every field except `sig`):

| Field | Meaning |
|---|---|
| `v` | `2` |
| `id` | ULID chosen by the issuer; unique per `(principal, id)` |
| `origin` | `{carrier, origin_id, origin_seq?}`: the first carrier's stable id; carried unchanged across rewraps |
| `target` | `{logical_session_id, execution_id?}`: the session it is for; `execution_id` is required for `approval.answer` and `control.*` |
| `action` | one of `data`, `user_turn`, `nudge`, `notice`, `goal.publish`, `goal.outcome`, `approval.answer`, `bind.change`, `seed.import`, `control.stop`, `control.park`, `control.restart`, `control.takeover`, `control.resume`, `terminal.attach` |
| `body_sha256`, `media_type`, `body` | the content; `body` may be a host-store reference for large items, but the hash is always in the signed bytes |
| `issued_at`, `not_before`, `expires_at` | the window; the maximum TTL per action is policy (default: `user_turn` 1 h, `approval.answer` 10 min, `control.*` 10 min, `data` 7 d) |
| `grant_refs[]` | mandate or grant ids that authorize `action` on `target` |
| `binding` | `{binding_id, binding_rev, policy_rev}` the issuer saw |
| `nonce` | 128 bit |
| `claimed_sender` | carrier display identity, data only |

`sig`: `{alg: ed25519, key_id, value}` over the canonical bytes. Required for every action except `data`, `notice` and host-generated `nudge`.

The bridge wraps an arrival in an **AdmissionRecord**, which is bridge-authored and never part of the signed bytes: `{envelope_digest, principal (derived), verdict, assurance_mode, binding_id, binding_rev, admitted_at, bridge_seq, bridge_sig}`.

## 3. Verdicts and what they allow

| Verdict | Who gets it | Delivered as | Effect authority |
|---|---|---|---|
| `authoritative` | Exact-byte signature by an operator key enrolled for this binding; `action` inside a valid grant; `target` matches; fresh; not revoked | the typed action (`user_turn` = a user turn) | only the action named and granted |
| `host_authored` | Text generated by host components themselves (nudge frames, notices, refusal reasons) | a framed host notice | none; it never embeds provider-chosen text without that text's own verdict label |
| `agent_authored` | Text the session itself wrote as a passive park note; own-goal provenance is deferred to SH2+ G2 (D-GOALS) | framed as "your own note" | none |
| `data` | A signed peer (a known agent key) on a bound channel | inside an `UNTRUSTED PEER EVENTS` frame | none; never answers an approval, never controls |
| `quarantine` | Any unsigned arrival | a metadata-only **doorbell**: channel, `claimed_sender`, count, `id`s. The body stays in the bridge mailbox; the agent reads it with `swarm-tail inbox read <id>` (a binding grant, §6), so it arrives as tool output, as in today's a2a pull boundary | none |
| `reject` | bad signature, wrong target, expired, replay, id conflict, revoked, unknown binding | nothing; a receipt `refused{reason}` and an audit line | none |

**Weak data-delivery mode** (owner exception, D-R2): a binding may be configured `unsigned_body: deliver_as_data`. It needs its own mandate, is shown in the plan and every receipt as `assurance: weak`, excludes `user_turn`, `approval.answer`, `control.*`, `goal.*`, `bind.change` and `seed.import`, and makes no complete-mediation claim.

**Assurance modes** (adopting B's T/S, H:659–680): mode **T** is same-UID: tokens, framing and the bridge are guardrails against mistakes, not a boundary against a hostile process of the same user. Mode **S** is a separated boundary (distinct UID or broker plus jailed tools) and is not claimed by any v1.2 path; a jail label alone does not prove it. A plan and a receipt always state the mode.

## 4. Host-enforced admission at every mutation

The session host exposes typed mutations only. Each one calls `admit(caller, action, target, evidence)` inside the host, against the host's own copy of grants, revocation snapshot, binding revision and admission fence (`restart-and-takeover.md` §2). The bridge's verdict is evidence, not the decision.

| Mutation (host API) | Required authority | Extra host checks |
|---|---|---|
| `enqueue(user_turn)` | `authoritative` envelope, grant `session.input` | fence open for dispatch; execution ready |
| `enqueue(data \| notice \| nudge)` | AdmissionRecord signed by the bridge (bridge identity = socket peer credentials + bridge key) | binding current; per-binding rate limit |
| `goal.*` | D-GOALS: launching caller at start through the launcher, or optional board/orchestrator for board goals; agent account has no goal-authoring capability (session host §3.8; `goals.md` §§1–3). Exact goal-client actions/capabilities unpublished | CAS on revision |
| `approval.answer` | `authoritative`, grant `session.approve` for this `target.execution_id` | `plugins-and-interactions.md` §2: pending interaction, exact native request digest, not expired, first valid answer wins |
| `bind` / `unbind` / `bind.change` | launcher or operator with grant `session.bind`; a binding change needs the binding's mandate | binding digest matches the project binding revision |
| `seed.import` / `restore` | host-signed HandoffPackage + recipient audience grant | per-item reauthorization (`handoff-package.md` §5) |
| `control.stop \| park \| restart \| takeover \| resume` | operator `authoritative` or a grant `session.control` held by the caller (S4 keeper, B4 for its own RUN) | fence state; explicit stops stay stopped |
| `terminal.attach` | grant `terminal.raw` (humans only) | exclusive input lease (`plugins-and-interactions.md` §3) |
| launch-time `goal`, `io_bindings`, `seed` | the launch caller's grants, checked at the `admit` stage of `launch.md` §4 | same rules as the matching mutation |

There is no untyped path to stdin. The only stdin writer is the context engine's dispatcher, and it only dispatches host-queue items that passed `admit`.

## 5. Durable, idempotent delivery

No distributed transaction (adopting C:676,698–708): two local atomic steps and an idempotent hand-over.

1. **Carrier → provider mailbox.** The provider persists the raw event (fsync) and only then advances its carrier cursor.
2. **Bridge admission (atomic, bridge-local store).** In one transaction: claim `(principal, id) → body_sha256`; compute the verdict; write the AdmissionRecord; state `accepted`.
   - Same `(principal, id)` and same hash: a duplicate; return the existing receipt.
   - Same `(principal, id)`, different hash: `reject: id_conflict`, audit, no delivery.
   - `origin_id` equal to an item this session posted through its outbox: `reject: reflection`.
3. **Durable host enqueue.** The bridge calls `host.enqueue(record, idem_key)`, where `idem_key = sha256(principal | id | body_sha256 | target.logical_session_id)`. The host writes the item to the session's durable inbox (fsync) and returns `ack{host_seq}`. The bridge marks `queued` only after the ack and retries until ack or `expires_at`. The host dedupes by `idem_key` for at least the retention floor.
4. **Dispatch.** At a turn boundary (or as a native steer, if the adapter supports it) the dispatcher re-runs `admit` (revocation, expiry, fence, readiness), writes the item to the adapter, and records `dispatched{host_seq, execution_id, input_marker}`.
5. **Application evidence.** The adapter confirms that the harness accepted the input (stream-json echo of the user message with the marker, the codex app-server item id, the muse serve ack). Then the state is `applied`. A pipe write alone is never `applied`.

Receipt states, sent back to the provider in order: `accepted → queued → dispatched → applied`, or `refused{reason}`, `expired`, `unknown`. The word "delivered" is no longer used.

**Unknown outcomes.** If the holder or host dies between `dispatched` and `applied`, the item is `unknown`. Reconciliation runs before the admission fence reopens (`restart-and-takeover.md` §3 step 8): the adapter searches the native transcript for the `input_marker`.
- Positive application evidence: `applied`, resolved without replay. Confirmed marker absence in an intact transcript supplies positive `not_applied` evidence; only otherwise eligible ordinary input may be retried after current admission checks. A timeout or failed evidence read is not proof of non-application.
- Unresolved evidence stays `unknown` and keeps the affected session's delivery fence closed. This supersedes the former once-only unknown `data`/`notice` replay exception (wiki Z18; session host §3.4). Authorised status/stop remain reachable; this is no global barrier.
- Unknown `approval.answer` and `control.*` are **never** replayed automatically. Historical approvals are void after any restart.
- SH1 compatibility remains; SH2+ receipt/state and recovery/disposition schemas still require publication and qualification. No operator override or automatic disposition is introduced for permanently undecidable evidence (session host §§3.4/7).

**Ordering.** Per `(target, origin)` stream, the host keeps a sequence. A gap holds later items up to `gap_wait` (default 30 s), then delivers with a gap notice.

**Retention and anti-replay floors.** Id claims and tombstones are kept for `max(expires_at) + 7 d`, at least 30 days. Arrivals with `issued_at` more than 2 min in the future or older than their TTL are rejected. The host keeps a monotonic high-watermark clock per store. A store restored from backup (a store epoch older than the recorded one) keeps the session's admission fence closed until an operator reconciles.

**Storage failure.** Disk full, fsync error or a corrupt store means `refused: storage` at whichever step failed. Nothing is acknowledged without being persisted.

## 6. Tails and `SWARM_SESSION_TOKEN` (tb-keeper condition 4)

- The token is in the agent's environment, so every subprocess inherits it. It is a **same-UID guardrail** (mode T), not a security boundary.
- Scope: one `{logical_session_id, execution_id}` and that session's own bindings. It is issued at the `initialize` stage, rotated on every restart (a new execution gets a new token), and dies with the execution.
- The passive `park <note>` needs **no mandate** and changes no goal revision. D-GOALS supersedes the agent-namespace `goal set|clear|status` surface: it is deferred to SH2+ G2, and the session token supplies no goal capability. Existing board outcome proposals remain proposals under the SH1 compatibility seam (`goals.md` §3; session host §3.8); no board-free completion or new goal-status/read API is defined here.
- Every other verb needs a **binding grant** issued by a mandate when the binding was created: `post <binding> <text>` and `inbox read <id>`. A grant is bound to one binding of this session.
- `post` is rate-limited (default 6 per minute and 60 per hour per binding; over the limit: `refused: rate`) and audited: an audit line `{session, execution, binding, body_sha256, at, verdict}` in the bridge's append-only log. Posts carry the session's agent identity and are `data` to any reader.
- Stdout markers are never parsed as commands.

## 7. Output egress

Output to a binding is filtered by an audience projection. The default projection is `final_text` (the assistant's turn text). Tool calls, tool results and the transcript go out only with a `transcript` grant for that binding's audience. Every posted item records which projection it came from.
