## 1. Principles

1. **An agent never holds a secret.** It asks a privileged neighbour to do something with the secret. What an agent cannot do physically, a prompt injection cannot make it do.
2. **Trust never rests on the transport.** Pipes are encrypted as hygiene; authority is only a signature over exact bytes plus a grant. Where a command came from does not matter.
3. **The kernel is the sandbox.** One OS user per autonomous agent; the kernel's user isolation, not a container or a prompt, is the boundary. (decided)
4. **Checks happen where the action happens**, never in the requester. One verification library everywhere.
5. **No free text in the authority layer.** Actions are registered names with schemas; free text reaches agents only as `data` or a doorbell.

## 2. Identities and the key keeper

- **Identity** = a stable derivation path plus its public key, never an OS path or UID: `purpose'/product'/project'/agent'` (hardened derivation, BIP-32/SLIP-0010; a child key reveals nothing about its siblings). (decided)
- **Root.** The keeper publishes the public root; the owner confirms it once at installation. Each agent identity is a public key plus the root's signature "descendant N". Anyone verifies the chain offline.
- **Keeper** (privileged daemon, the only holder of the master secret in Secure Enclave / TPM / DPAPI-CNG where available; on macOS a LaunchDaemon with the System keychain). Own-key signing and decryption use kernel peer credentials (`LOCAL_PEERCRED` / `SO_PEERCRED`), never a caller-claimed identity. Registration binds `(uid, generation, identity path, owner, registration generation)` and records the one-shot flag. The keeper checks the active ledger before signing and detaches registration before UID reuse. No API returns a private key; key pairs are never placed in an agent's keychain. The registration/revocation API and the broker migration procedure remain unpublished; integration stays disabled until their joint publication and qualification (dispatcher §14, user manager §4.4, broker §4.3). No bridge on-behalf signing operation is adopted.
- **Decrypt** returns plaintext only to the calling process, audited and rate-limited. The keeper protects the key, not the plaintext: packages are addressed only to whoever must read them and carry nothing extra.
- **Lifecycle (D-IDENTITY).** Account retirement and registration detachment are separate from identity revocation. Only the dispatcher that registered an identity with a recorded one-shot flag may revoke it, as a separate journaled effect after confirmed account retirement; retries reuse that effect ID and unknown/refused results keep the cleanup obligation pending. Account names and retirement requests cannot supply the flag. A standing identity survives normal account retirement and requires an operator-signed revocation. Migration of the same identity is subject to the broker's gated migration procedure (dispatcher §14, user manager §4.4, broker §4.3).
- **External identities** (other organisations, remote workers) bring their own key pair: a self-signed certificate is verified, the public key is pinned, and the root signs an admission record "external key K admitted with role R". Both kinds live in one registry under the same checks.
- **Risk.** Master-secret compromise compromises everyone: the keeper stays minimal, privileged, audited.

## 3. Grants

- **Record.** `grant/1 {issuer, subject (key or role), actions[], targets[], conditions{lang, …}, delegable{depth}, parent?, expires_at, sig}`. Role bindings are separate signed records, so a grant to a role covers whoever holds it; playbook role rights are grants to roles.
- **Delegation with attenuation.** A requester may grant at most a subset of what it holds and of what is marked delegable: subset of actions and targets, expiry not later, depth not deeper; `parent` links the chain to the root. The dispatcher refuses a spawn whose requested child grants exceed the requester's delegable grants. Inspiration: SPKI/SDSI, Macaroons, UCAN, Biscuit (Biscuit's Datalog and offline verification are a candidate implementation). (proposed)
- **Conditions and the policy language.** `conditions.lang = caveats/v1` today (time windows, counters, operator confirmation, target lists); `datalog/v1` or similar later. One library with pluggable evaluators; envelopes carry only grant references, so a policy language never changes wire formats. (proposed)
- **Checking.** The task core checks role grants when it moves a task or accepts a result; the dispatcher checks spawn grants; the broker checks "may write to this agent" before delivery; the bridge checks the audience on the way out. An orchestrator asks; it never judges.
- **Issuing and syncing.** Grants are managed in the owner's client app and synced through a signed trust gateway into the registry; services subscribe to revocation snapshots and re-admit at dispatch. Where the registry lives (git journal, Matrix state, a service, a hybrid) is **open**.

## 4. The action vocabulary and handlers

- **Vocabulary.** A registered set of namespaces, each with argument schemas and a handler: platform base `session.*`, `goal.*`, `board.*`, `user.*`, `spawn.*`, `post`, `inbox`, `terminal.raw`; later e.g. `github-runner.*`. Targets are typed resource ids (`session:…`, `host:mini/runners/x`, rooms, board elements); wildcards only in grants, commands name a concrete target.
- **Registration** (three signed records):
  1. `handler-manifest/1 {handler identity, actions{name: args schema}, target form, effects: reversible|irreversible, sig}` published by the handler;
  2. `action-namespace/1 {namespace, handler, manifest_sha256, hosts[], grantable_by[], issued_by (chain), expires_at, sig}` issued by the owner or by an agent holding `registry.actions.register` — attenuated, e.g. only inside `ops.*`; the same name again only with the same handler or a root-signed replacement; removal is a revocation;
  3. grants and commands name the registered action. A grant on an unregistered action is refused at issue; the gate validates arguments against the manifest.
- **Handlers.** A *process* handler (deterministic helper) for OS-level and irreversible effects re-verifies the chain itself, executes exactly one registered operation, audits and signs its receipt. An *agent* handler (e.g. an admin orchestrator with wide grants) receives a typed `authoritative` item with a verification record, may re-verify, adds judgement, and executes with its own permissions (a narrow sudo rule or the helper); it cannot amplify. `effects: irreversible` hints that a process must handle it.
- **Worked example.** G1: root → Alexis's pinned key, `github-runner.{restart,stop}` over `host:mini/runners/*`, caveats (hours, rate), delegable depth 1. G2: Alexis → his orchestrator, a subset, `parent: G1`. His orchestrator sends `swarm-envelope/2 {action github-runner.restart, args{runner x}, target host:mini/runners/x, grant_refs [G2, G1]}` signed by its keeper. Our gate verifies signature, pin, chain, attenuation, schema, caveats, revocation; the registry names the handler; a receipt returns signed. Sequences `action-namespace-registration`, `delegated-action-handler`.

## 5. Agent workplaces (one OS user per agent)

- **Every autonomous agent** — meta-keeper, keepers, orchestrators, standing specialists, ephemeral workers, remote workers' workplaces — runs as its own OS user. (decided)
- **Creation** by one narrow privileged helper that sudoers admits for the dispatcher (and nothing else); the helper creates the user, its group, the home and (v1) the firewall rules, within the caller's account-count quota, and removes them at retire. It sets no ACL. Resource ceilings are not part of account creation: they apply per execution where the host can enforce them (owner decision 2026-10-13). A system-administrator *capability* is a grant (`user.create`), not an agent.
- **Network.** The kernel firewall per UID (pf `user`, nftables owner match, WFP) admits only the account's own listener of its bound network profile; everything else is dropped and counted. The broker and the other platform services are reached over Unix sockets, which the firewall does not filter. A workplace admits nothing (§7.6). This makes network profiles enforced rather than cooperative.
- **Which profile (review F-27, accepted 2026-10-12; v1 with enforcement).** A caller never chooses a child's egress. A root-owned, agent-readable binding policy maps the admitted Curator profile identity (its name **and** lock digest, so a profile of the same name in a caller's home cannot redefine it) to exactly one network profile reference and digest; on a platform host it never names `direct` or an external proxy (owner decision of 2026-10-13, below). Grant `profiles` already narrow down a delegation chain, so egress narrows with them; a separate network grant dimension is added only if one Curator profile ever needs several egresses. The dispatcher resolves the binding at admission and pins reference and digest in the request record; a policy change before the rules are applied refuses instead of applying another profile. The proxy runs one listener per bound account generation, so caps and logs know the account. It publishes per listener the digest of the policy it actually serves (allow entries, caps, guard version), and the firewall apply refuses unless it equals the pinned digest, so the applied-state record certifies a served policy, not a label; a reload or port reuse never changes the egress of agents already bound. Narrowing reaches running agents through a journaled re-apply: the kernel side flushes the account's states, the proxy drops or re-checks sessions of the old allowlist. In v0 the selected profile is recorded as declared only.
- **Platform accounts have egress policies too (review F-24, accepted 2026-10-12; v1).** Every non-root account under `/opt/swarma` has a row in one published matrix, installed in the same helper-owned anchor or table as the agent rules: the dispatcher and the session host **deny all** (they speak only Unix sockets, which the firewall does not filter; loopback TCP included); the broker reaches its vendor only through **its own network profile and proxy listener**, with the vendor names in the proxy allowlist (kernel rules per vendor address are brittle and admit every other tenant of a shared front end); the proxy's own account is **proxy-enforced**. Root-run components (user manager, launcher) get no per-UID row; a root sandbox would be a separate qualified mechanism. Rows are re-verified at every service start and on a published schedule; a missing row drops that service's readiness and is reported (detection with a defined response, not continuous enforcement). **Name resolution is a separate channel:** on macOS a lookup leaves the host as the root `mDNSResponder`, on Linux as `systemd-resolved` under `nss-resolve`, so per-UID packet rules are not DNS evidence; accounts behind a CONNECT proxy need no local resolution, and accounts that never need names get a sandbox that denies the resolver. The claim is bounded: allowed destinations can still carry data, so the matrix reduces uncontrolled egress; it does not prove a store cannot leave.
- **Internet and builds (owner decision, 2026-10-13).** Inside our environment an agent's account has no internet beyond what its own agent loop needs.
  - **Trusted local agents** reach, through their own listener, only the model-provider endpoints of their qualified tuple. The proxy enforces the admitted `CONNECT` authority and the address it checked and dialed, not the application inside the tunnel. So an allowed destination can still carry data out, and a shared front end can serve another site behind an allowed name (domain fronting). No TLS interception is added; a stronger claim for a tuple needs its own evidence (network profiles N15 item 11; review F-33, accepted 2026-10-13).
  - **A workplace** reaches nothing (§7.6).
  - **Web access is off by default** (owner, later the same night). The design works without it:
    - a task carries the resources it needs, such as fresh documentation, read-only and by digest, and the trusted side fetches more on request;
    - the donor's loop reaches only its provider's endpoints and our host;
    - our side has no internet.
  - **Search is an opt-in** for trusted-circle identities only. The operator grants it per identity, and never to the untrusted class. Its forms are:
    - provider-side search, which no network rule sees, so the launch plan keeps it off unless the identity holds the opt-in;
    - a donor-side MCP server holding the donor's own key (§7.2);
    - for local agents, a platform web-tool service whose key never sits in an agent account, reached over a Unix socket with a grant.
  - **Builds and tests.** Agents neither build nor test. A controlled verification phase runs builds and tests on ephemeral runners on another machine, without secrets, and dependencies are fetched only there. The fetch step runs no candidate code, and the build and test step has no route out, whether or not the job is vendored (network profiles N16; review F-50, accepted 2026-10-13).
  - **Repository effects (open; review F-56, accepted 2026-10-13).** No agent account reaches a code host. Publishing a pending candidate ref, handing the candidate bundle to the runners, refreshing the base and landing the accepted head need a performer that is not an agent. The performer is an owner and infrastructure choice and is not chosen here. If it is a non-root service on a platform host, it gets its own row in the table below and in network profiles N15 item 7, and the runner-pool ingress needs a placement the dial guard does not refuse. Whatever performs an effect holds the credential and checks the verdict and the fast-forward itself; it never trusts the requesting agent.
  - **The egress proxy.** A platform host never binds `direct` or an external proxy. The proxy serves:
    - `host:port` allow entries;
    - refused mail and resolver ports;
    - a dial guard against private, tailnet and metadata ranges;
    - per-identity caps and logs.

  Details: network-profile specification N15 items 2, 5 and 10–12, and N16 for the runners' egress.
- **Homes.** Every agent and workplace home is created empty under the user manager's fixed agents root, owned by the account, mode 0700, with no ACL and no supplementary groups; orchestrators and workers are treated alike. A parent does not read a child's home by default; an explicit opt-in read delegation is a later (v2) capability of the user manager. Observability comes from the host (journal, transcripts), board results and handoff packages. Code leaves a child's home only through the transfer path the owner decided on 2026-10-13: the platform exports a change set after the work stops, the board imports it as a signed candidate commit, a trusted reviewer reviews that exact commit, and it lands by signed fast-forward; rework returns to the worker on top of the candidate.
- **Ephemeral trees.** A "cheap tree copy" abstraction: APFS clone on macOS, `cp --reflink=auto` on Btrfs/XFS (a plain copy on ext4), overlayfs optional. Session logs stay out of git.
- **Git across accounts (review F-16, accepted 2026-10-12).** A linked `git worktree` is not a separate repository: its administration points back into a common directory with shared refs, configuration and hooks. So linked worktrees stay **within one account** (today's board workflow is unchanged). Across mutually isolated accounts the default is a **standalone repository under the agent's home** with its own `.git`, refs, index, configuration and hooks, materialised from the admitted base with freshly written local configuration, never with the parent's `.git` backlink, local configuration, hooks or credential helpers; clone and reflink optimisations keep that rule. Shared objects, if any, are immutable, read-only to agents and limited to authorised sources. Source and results cross private homes only through the approved repository or artifact path, never by widening home permissions or a recursive root `chown`; who transfers them is published before cross-account workspace launches are enabled. The transfer path itself is decided (owner, 2026-10-13; Homes above). The board's import contract and the dispatcher's `workspace-result/1` are not yet published.
- **Stable team.** A project binding declares `team[] {role, identity, standing|ephemeral, max}`; S4 `up` brings standing members back idempotently after a reboot; ephemeral users are created per run and removed at retire.
- **Privilege model.**

## 6. Entry channels and the message path

- **Three entries.** *Root channel*: the operator only, locally — a signed command or a terminal under the exclusive lease (`terminal.raw`); the host writes straight into the PTY. *External channel*: carrier plus broker — the only path for every external party, external orchestrators included; never the root channel. *Join point*: a one-time HTTPS endpoint for introductions (certificates in, credential packages out), never commands; unnecessary when the package travels out of band. (decided)
- **Agents never read the carrier.** The broker (the room member) holds carrier credentials. A provider persists each raw event (append, fsync) *before* advancing its carrier cursor, then hands the bridge an envelope; a replay after a crash is harmless because admission is idempotent per (sender, id).
- **Trust gate**, pure library, no network, no model: canonicalise (JCS) → find the key by `key_id` in the registry snapshot → verify Ed25519 → derive the sender → load `grant_refs` and walk the chain to the root (each link signed by its issuer, subject = next issuer, actions/targets narrowing, expiries nested) → revocation snapshot → time window and replay journal → target binding revision → verdict and an admission record signed by the bridge. Any failure is `reject` with a reason and an audit line.
- **Decision guard.** After the gate, a small local model compares the request with the addressee's grant specification and injection patterns and records `{body hash, sender, grants used, model version, verdict, fingerprint}`; the host rings the doorbell; the agent fetches body plus verification record from the **Mailbox** (`inbox read`, In and Out) and may re-verify. If the guard is unavailable, the answer is no.
- **Who may write In / read Out.** By default only the parent (granted automatically at spawn); everyone else through the broker. The owner, as root of trust, holds every grant. **Proposed.**
- **Encryption.** Signatures over the carrier's own end-to-end encryption; no envelope encryption of our own for now. People use ordinary clients; signatures ride in event metadata. (decided)
- **Federation test.** The owners' two-domain setup (own Matrix servers, machines, regions; shared rooms for shared projects) is the reference test for federation and onboarding after the single-host MVP.

## 7. Remote workplaces

Detailed by Curator's CIP-0008 (lockdown launch mode), CIP-0009 (donor-side deployment and bridge) and CIP-0010 (credentials), revision 2 after the architecture review of 2026-10-08 (curator-spec PR #134 at `5100b46`, draft). Everything in §7.2–§7.9 is **proposed** unless marked; points waiting for the owners' answers are listed in §7.10.

### 7.1 Shape (decided)

A remote worker's harness runs on the **donor** machine and does all its work on our host. On our host it gets a workplace user; one SSH connection goes from the donor towards our host and carries tool execution and the mailbox; our host never opens connections to, or sends commands into, the donor machine. Remote workers use their own provider credentials; ours never reach the donor, and the donor never receives carrier credentials.

### 7.2 The donor machine: three deployment variants

**Decided 2026-10-10 (CIP-0009 D0).** The strongest donor boundary needs two OS identities, which need administrator rights once; the owner does not want a donor asked for those rights by default («для него это будет красный флаг»). Hence three variants; `init` records the variant in the enrolment and in the qualified tuple, a project's workplace policy may require a minimum variant (for example write access only for B or C), and `status` and the session banner name it.

| Variant | Administrator rights | Donor-side boundary | Bridge runs as | Keys | Order |

Lockdown only** | none | the §7.3 lockdown posture with strict qualification (R9): the model is offered no local tool and only an exactly qualified harness build starts; no OS boundary beyond the donor's user | a user service of the donor (macOS LaunchAgent, Linux `systemd --user`), while the donor is logged in | non-exportable Secure Enclave keys on Macs that have one (P-256 signing and SSH keys; the transcript's `algorithms` names them); 0600 files in the donor's state directory on Linux, TPM later | first milestone |

Two identities** | once, at `init` | the untrusted harness identity and the trusted bridge identity below, per-UID egress, the kernel read boundary, a root-owned executable root | the bridge identity, as a system service that survives logout | 0600 files owned by the bridge identity, **no Keychain**; non-exportable keys later only if the Secure Enclave proves usable from such a service without Keychain | proposed stronger boundary; disabled until the separate donor provisioner is specified and qualified |

- **A states its limit.** If a qualified harness build turned out to offer a local tool after all, the model would act as the donor's user. That is the accepted risk of the first milestone; exact builds checked before exec and the bridge's posture check (R9) are its guards.
- **The lock without a system layer.** In A and C the locked configuration lives in the donor's own files: the harness cannot change it (A: no tools; C: outside its writable set); the donor can, and then the bridge stops the worker instead of running it open.
- **Executables.** In A and C under the donor's state directory (`~/Library/Application Support/swarma/<release>/`, `~/.local/share/swarma/<release>/`), each digest verified before exec; in B under the root-owned `/opt/swarma/releases/<release>/`.
- **Egress.** B: per-UID firewall rules; C: the sandbox's network rules; A: none of its own, the harness reaches its provider directly. By default the donor's loop has no web access and reaches only its provider's endpoints and our host. In A its locked configuration ensures this; in B and C these egress rules also enforce it. For a trusted-circle worker the operator may grant a donor-side MCP server holding the donor's own key. That server runs under its own identity in B or under its own sandbox profile in C, never in the harness or the bridge identity (owner decisions 2026-10-13; CIP-0009).
- **Order (owner):** A on macOS and Linux first, then B on macOS, then C (Seatbelt under the donor's user, then Landlock or bubblewrap on Linux).

**Variant B in detail (CIP-0009 D1, D2):**

- **Untrusted harness identity** `swarma-rw-<project>`: the harness in lockdown (§7.3) plus the stdio relay `swarma-remote-tools`, which holds no keys and has no network; home 0700, no login, quotas; owns only its managed home and scratch directory.
- **Trusted bridge identity** `swarma-rb-<project>`: keys, locked configuration, audit, cursors. The bridge service runs as a `launchd` system daemon (survives logout, needs no login keychain): it holds the single SSH connection, serves the relay over a Unix socket that checks peer credentials, signs outgoing envelopes, admits incoming items, keeps the budget counters (the trusted side's counters are authoritative) and executes `stop`. The supervisor `curator remote-worker run` is part of it and starts the harness **as the harness identity**.
- One identity for both was rejected by the review: with a shared UID the per-UID firewall distinguishes nothing, and a shared home exposes audit, state and keys.
- **Separate donor provisioner (D-DONOR-PROVISIONING).** Variant B remains disabled until its separate short specification, rules, removal contract, closed schema, binary name and privileges are published and qualified. The remote-worker publication register owns this pending item (CIP-0009 D1/D2); user manager §1 non-goals excludes donor provisioning/removal. Its `user.create`/`user.retire` are not substitutes and gain no donor verbs. UID/path libraries may be reused without sharing donor privileges.
- **Egress by UID** (`pf` anchor): the harness reaches only the local provider proxy (an allowlist of provider hosts per qualified tuple); the bridge reaches only our SSH host and the join point; nothing inbound.
- **Sandbox**: a Seatbelt profile for the harness process with an explicit allowlist (read and execute the protected binary root and runtime libraries, read/write the managed home and scratch, connect to the relay socket and the proxy port); everything else denied. The **read boundary is mandatory**: it neutralises read-only tools that a harness cannot remove (Muse) and keeps the bridge home closed even if file modes were wrong. The profile revision is part of the tuple and the plan.
- **Protected binary root** `/opt/swarma/<release>/`, root-owned, read-only, no writable parent; the bridge starts every binary by absolute path and checks its digest against the release manifest. The MCP pin covers the relay's declaration; the binaries are pinned separately.
- **Transactional install**: a journal per step and reverse-order rollback; an interrupted install never leaves a weakened rule. The separate provisioner's exact operations remain unpublished.
- **Keys**: per the variant table above (decided 2026-10-10); in B 0600 files of the bridge identity, no Keychain.
- **Platforms**: macOS first (what `rwh` measured); Linux next (two system users, `nftables` by UID, `systemd` service, harness via `systemd-run --uid` with `NoNewPrivileges`, a cgroup for lifetime, **Landlock** as the read boundary); Windows no. An unsupported host is refused at `init`.
- **Negative tests on real inputs** (`init`, launch, tool call, stop): reads outside the allowlist, egress outside it, the proxy refusing a foreign host, the socket refusing a foreign UID, the separate provisioner refusing a repeated label, a symlink in a path, an arbitrary account selected for removal, argument injection; an install interrupted midway rolls back.

### 7.3 Lockdown launch mode (CIP-0008)

- **Tool posture** `tool_posture.<profile>` = `open | lockdown`, a *machine* setting the donor locks in system configuration. The lock rule is amended: a lock may fix exactly the pair `lockdown` + `remote-auto` (a lock still never selects credentials).
- **Permissions `remote-auto`** ("marked yolo"): the relay's tools are pre-approved, everything else that would ask is denied silently, and no native bypass appears in any source (flags, settings file, configuration key); its presence alone is a refusal. Allowed only with `lockdown`; each harness has a headless and an interactive spelling, each with its own test.
- **Qualified tuples** instead of "version ≥ x": exact version, binary digest, platform, transport, model, settings policy, sandbox revision; any update is a requalification; a tuple without a row is refused. Rows today: Claude Code 2.1.293 (`--restricted --tools "" --strict-mcp-config --mcp-config <protected> --settings <protected> --setting-sources "" --disable-slash-commands`, protected files owned by the bridge identity, the system managed policy read and refused if it enables bypass, MCP or hooks, empty cwd, never `--bare` because it does not read OAuth); Codex 0.159.0 over **app-server only** (managed `config.toml` as base configuration, `sandbox_mode = read-only`, approvals routed to the supervisor and refused, web search, analytics, hooks, plugins and 23 feature switches off, empty tool list, pruned model catalogue, pinned model, `--strict-config`; `codex exec` only after its own qualification); Muse 1.4.3 on macOS only (`--disable-shell --disable-write --disable-web-tools --no-foreign-personal-context`, session logs kept under quota as untrusted data; read tools cannot be removed, so the OS read boundary is mandatory) — **not admitted for donors** (R9, below): a lab row until the read boundary is accepted as a guarantee. Updaters, telemetry, logs, settings, hosted tools and instruction discovery are inventoried per tuple; telemetry and updates are bounded by the UID egress allowlist, not by flags.
- **Launcher grammar**: the *generated policy* (written by agents-management) is mandatory, and a plan where a member is missing, duplicated, aliased or set from another source is refused at admission; the *caller tail* after `--` is parsed against a closed per-harness allowlist (Claude: `--output-format`, `--verbose`, `--resume`, `--session-id`, `--max-turns`; Codex app-server: nothing). Errors: `tool_posture_conflict`, `tool_posture_unknown_argument`; an unknown harness or tuple is refused.
- **Plan and policy generation**: the posture is a mandatory plan extension (an admission that does not know it refuses); the machine configuration keeps a policy-generation counter that the composer copies into the plan and the final executor re-reads at launch and at every resume, refusing on mismatch; changing `tool_posture` or the permissions stops a live session at once. A donor supervisor's statement about its kernel is a statement, not an attestation, and is recorded as such.
- **Owner decisions of 2026-10-10 (CIP-0008 R9, decided).** *Admission rule:* «среды которые проверенно не умеют выключать тулы (а также для которых нет обходных путей отключить тулы с гарантией) мы пока не поддерживаем». *Strict qualification at launch:* «для удаленного работника нужна будет более строгая политика запуска сессии так что бы могли запускать только проверенные без оптимистичного поддержания новых» — a remote-worker session starts only an exact qualified tuple; the executor checks the executable's digest against the central qualification feed **before exec**; an unknown, newer or unqualified build refuses with no warning-only path; a self-updating launcher is never executed; a last-known-good fallback may select only another qualified tuple. *Pi 1.1.0 and OpenCode 1.18.35 are wanted* («они нам очень нужны для удаленных воркеров»): candidate configurations exist, each is qualified on hosted macOS and Ubuntu runners before a row exists. *The bridge enforces the posture too:* the donor-side supervisor refuses a session whose effective posture is not `lockdown` + `remote-auto`, and a posture change stops a live session; where the lock lives in the donor's own files (variants A and C) an edit can stop a worker but never open one silently. Also decided: the names `open|lockdown` and the profile `remote-worker` with no separate launch mode; the donor's one-time consent recorded by `init`; Codex through the app-server only, `exec` after its own qualification.
- **No second compiler**: agents-management composes through the single construction site; the remote-worker supervisor only consumes the composed plan, like the session host. Amendments to Decisions 0019/0021 are needed before implementation.
- **What the donor sees and can do**, locally and without us: `curator env status` (posture, tuple, generation, permissions with an honest sentence, relay, project); an audit line per tool call written by the bridge identity (name, argument hash, sizes, time, no content); `stop`, `leave`, `purge`.
- **Honest banner**: "no local tool is offered to the model; the harness runtime keeps its managed state; tools execute in the project's workplace" — not "nothing can be done on this machine".
- **Layers, strongest first**: two OS identities, kernel sandbox and UID egress on the donor; no local tool offered to the model; launcher grammar and admission checks; the executor's tripwire and audit (detection after dispatch); the workplace policy on our host.

### 7.4 Join (CIP-0009)

1. **Invitation** `swarma-invitation/1`: id, join point, root fingerprint, SSH host-key fingerprint, project, role, expiry, and a one-use random code of at least 128 bits (a short-lived bootstrap secret), delivered with the invitation through whatever channel the donor found us by (a marketplace thread, an e-mail, our site); there is no human second channel (decided 2026-10-10: a donor is often someone who only heard of an environment). A person who only knows our domain runs `init <domain>` instead: an open application that waits for the operator.
2. `curator remote-worker init <invitation>` is run **only by the human owner of the machine** (decided, D10): an interactive terminal and a typed confirmation of what is installed, under which variant, and what the worker may do; it refuses without a terminal or inside a managed agent session. It refuses an unsupported host, sets up the chosen variant (in B through the helper), and the bridge identity generates **three role-separated keys**: `K_sig` (Ed25519, signing), `K_enc` (X25519, package decryption), `K_ssh` (SSH). An enrolment certificate over the three keys, name, role, invitation id and expiry is self-signed by `K_sig`; its fingerprint is shown. (Supersedes the single key pair and `swarma join` of the v1.3 text; the command name is open, §7.10.)
3. **Server challenge**: `POST /join/challenge` returns a challenge bound to the invitation (5 minutes, attempt counter). **DNS check, mandatory (decided 2026-10-10)**: Curator validates DNSSEC itself from an embedded root trust anchor, so the donor installs nothing («ок делаем так»); it fetches TXT `_swarma.<domain>` (root fingerprint), the SSHFP records of our SSH host, TXT `_swarma-ssh-ca` (the host CA, §7.5) and the TLSA record of the join point through the system resolver and, when the network strips DNSSEC data, through DNS-over-HTTPS resolvers («ок. в идеале»); the signatures are validated locally either way. A *secure* result must equal the invitation's fingerprints when an invitation exists; *bogus* or *indeterminate* refuses with an explanation; nothing downgrades. A closed network with its own DNS takes the zone's trust anchor from the network's configuration or the invitation; an environment without a DNSSEC domain falls back to the invitation's pins (owner, 2026-10-10: DNS-published keys are the default for environments that recruit agents, «для операторов общей среды не проблема зарегистрировать домен и положить туда ключ»).
4. **Transcript** `swarma-join/1` (deterministic CBOR, domain-separated: version, invitation id, project, role, three keys, server challenge, client nonce, expiry, algorithms), signed by `K_sig` and posted with the code over HTTPS validated by the Web PKI for the join point's domain and pinned by its DNSSEC-validated TLSA record (and by the invitation's certificate fingerprint when there is one). The join point checks the code in constant time, the signature, the challenge binding and the expiry, **consumes the invitation atomically** (a tombstone per invitation id: a retry with the same `K_sig` returns the same pending enrolment, another key is refused), rate-limits, and accepts only three verbs (challenge, cert, collect).
5. **Admission (no voice comparison, decided 2026-10-10)**: the operator, or an orchestrator with the `onboard` grant plus operator confirmation, checks the enrolment against what is known of the donor — the key in the donor's signed marketplace card when there is one, otherwise the invitation the code binds — then pins the three keys, the root signs the admission, grants are issued. The **package** `swarma-credential-package/1` (root key, operator certificate signed by the root with scope `onboard`, host, SSH host key, workplace user, binding digest, qualified tuple, policy generation, expiry) is encrypted to `K_enc` (X25519 + HKDF + ChaCha20-Poly1305, transcript digest as associated data) and signed by the operator certificate. It carries **no carrier identity and no tokens** (supersedes the v1.3 text).
6. **Collect** with a second challenge signed by `K_sig`; the bridge decrypts, verifies the operator certificate against the pinned root, the package signature and the associated data, writes the locked configuration and binding, installs the relay declaration, and reports "registered, waiting for tasks".
7. The dispatcher provisions the workplace on our host (§7.5).
8. **First contact rests on three independent checks that must agree** (D6): the Web PKI certificate of the join point's domain, the DNSSEC-signed fingerprints validated inside the client, and the invitation's pins when an invitation exists; plus the one-use code and the server challenge bound by the signed transcript. An attacker would have to forge the invitation's path, the DNS signatures and a certificate for our domain at once.

### 7.5 The bridge protocol `swarma-rb/1` and our SSH side

- **SSH**: one connection from the donor bridge under the workplace user with `K_ssh`; our host key is checked against the pin (and SSHFP when secure) on **every** connection; no trust on first use. Our `sshd` has a `Match` block for workplace users: a **root-owned authorized-keys file outside the user's home** (a shell tool cannot append a key), `restrict` and a forced command by absolute path, `PermitUserRC no`, `PermitUserEnvironment no`, no agent, port or X11 forwarding, no PTY. **The forced command is a stub, and it is also the account's login shell (review F-19, accepted 2026-10-12).** `sshd` runs a forced command through the user's login shell with `-c`, so a real shell would read worker-written files (`~/.zshenv`; `~/.bashrc` in bash builds with `SSH_SOURCE_BASHRC`) at the next connection, and `PermitUserRC no` covers only `~/.ssh/rc`; with the user manager's usual no-login shell the forced command would not run at all. The workplace is therefore its own account class: its login shell is a fixed root-owned binary in `/opt/swarma/libexec/` that accepts only `-c <forced command>`, reads no user file, and relays the channel to the workplace service's peer-authenticated Unix socket.
- **SSH certificate authorities (decided 2026-10-10, D12).** *Hosts:* one host CA key (Ed25519), held by the key keeper or on a hardware token, never on a host, signs each host's key into a certificate that names the host and expires (about a year, renewed automatically; `HostCertificate`); the CA's public key is published once as TXT `_swarma-ssh-ca.<domain>` under DNSSEC and delivered in the credential package; the client writes `@cert-authority`; adding a host changes no DNS record; revocation by `RevokedHostKeys`; a CA rotation overlaps. *Workers:* each worker's own keys are generated on the donor and pinned in our registry, never published; a separate user CA signs `K_ssh` into a short certificate (about a day, principal = the workplace user), renewed over the authenticated channel by a signing service whose key custody is named and which issues a certificate only for the principal of the authenticated workplace that asks (F-19); sshd trusts it with `TrustedUserCAKeys`, so expiry and revocation live in one place. How the forced command and `restrict` ride with certificates (certificate options or a root-owned principals file) is for CIP-0009's next revision.
- **Carrier server (decided 2026-10-10, D11).** The platform's Matrix server is configured for least access from the start; today's experimental swarm server is not the model: invite-only rooms absent from any public directory; an account gets exactly the rooms of its role, invitations and power levels issued by operators or the bridge, never self-served; organisation members get accounts limited to their rooms; freelancers keep marketplace accounts and join through federation enabled only towards allowlisted servers. The first slice keeps the worker's carrier identity in our bridge; from the second slice the worker posts with its own account and our bridge only verifies — a worker's messages always carry the worker's signature.
- **Frames**: a 4-byte length checked **before** allocation (maximum 1 MiB), deterministic CBOR without duplicate keys, `hello` with versions, request ids scoped to the connection, and a client **`op_key`** for idempotency. **Effect claims are durable and separate from the result cache (review F-7, accepted 2026-10-12):** before any mutation (`exec`, file writes, patches) the workplace service durably claims the binding-generation-scoped operation identity and the canonical-argument digest; a retry keeps its identity, arguments and admission window; a mismatching reuse refuses; a known claim without a result answers `unknown_result` and is never re-executed; requests carry an authenticated freshness window so claims can be discarded after it closes; a lost or restored claim store keeps the workplace closed until reconciled. Results themselves are cached for ten minutes only.
- **Methods**: `exec`, `cancel`, `stdin`, file operations, `mailbox.read`, `mailbox.post`, `mailbox.applied`; from the server `mailbox.notify` (advisory) and `policy.changed`. **The server's policy is authoritative**: timeouts, output ceilings and leases can only be lowered; `cancel` and `stdin` apply only to the caller's live job; every method is authorised by the policy; flow-control credits; environment variables only from `env_allow`.
- **Who enforces (review F-19, accepted 2026-10-12).** Nothing that enforces policy runs as the worker. Policy, the tool intersection, caps, effect claims, our-side audit, certificate renewal and the mailbox control plane live in a **service principal** (the bridge daemon or a dedicated workplace service account); the stub only relays. A job that impersonates the stub from inside the workplace gains nothing: posts still need the donor's `K_sig`, reads return the worker's own mailbox.
- **Job lifetime**: worker jobs run under the workplace account as **launcher-started executions** with a start receipt and the platform's journaled stop, which proves that no process of the generation started after the receipt survives. A same-UID process group or a cgroup the job could migrate out of is not proof. Two shapes stay open until the workplace wire freezes: one job at a time as one execution (exact proof per job), or one standing workplace runner per workplace that spawns jobs on the service's instruction and holds no authority; in that shape a per-job `cancel` is best effort, and when a job's descendants cannot be confirmed gone the service stops the whole runner execution, keeps every affected job's claim as unknown, never replays it, and restarts the runner. Lease expiry, `cancel` or a transport drop after a grace period triggers these stops — a test at execution granularity, not an assumption.

### 7.6 Workplace backend contract `swarma-workplace-exec/1`

The first backend is the workplace as an OS user (§5), as its own account class: the stub as login shell (§7.5) and **zero egress** (owner decision, 2026-10-13): no network profile, no proxy destination, loopback denied. The user manager installs that denial in the same locked operation that activates the account, the job sandbox denies name resolution, and no service with egress admits a workplace principal. The inbound SSH entry is not workplace egress, so egress denial is no ingress fence either: a donor's reconnect can start a new relay under the workplace account during quiescence, export, a watcher stop or the all-stop. The relay's lifetime and a generation-bound ingress fence are open (review F-38, accepted 2026-10-13; §7.5) and gate this backend like the rest of this section. The worker's model calls happen in its agent loop on the donor's side. Builds and tests do not run in the workplace; they run in the verification phase on off-host runners (§5). **A remote workplace is admissible on a host only after the per-UID firewall with published applied state (user manager v1, broker slice 2) runs there (F-19).** A workplace leases nothing on our host, so the broker's network gate never fires for it; the activation gate is the only one. Variant A is a donor-side posture and does not exempt our side. Loopback is a hard row of the workplace's firewall matrix, because local TCP services on our host are the lateral path; Unix sockets stay unfiltered, so the broker, dispatcher and host sockets, and every service with egress, refuse a workplace principal without a configured role. Host-local workplace jobs are a newly qualified backend, not something the dispatcher's subset already supports. The contract lists what any backend must give: an execution API with ceilings; a per-worker policy (tools, write scope, network, limits, `env_allow`) whose id appears on every audit line — on the OS-user backend `write scope` **is** the account's writable set and `network` **is** its firewall row, so its only value is `none`, and fields a backend cannot honour are removed rather than kept as labels; the tool-set intersection; audit on our side; review and export of changes as a patch; cleanup. The maximum tool set is `bash`, `read_file`, `write_file`, `apply_patch`, `mailbox_read`, `mailbox_post`; the **effective** set is its intersection with the workplace policy (a read-only worker gets `read_file` and nothing else). `write_file` and `apply_patch` count as execution for the gate above: a write into the workplace's files can become code that runs under its account, so there is no early read-write exception before the firewall exists. No `enrol`, `key` or `config` tools. A container backend joins through an adapter only after its own qualification; its guarantees are not borrowed.

### 7.7 Signing and delivery

- **Signing on the donor side.** `K_sig` never leaves the donor's bridge identity. The donor bridge builds the **final** envelope (canonical bytes with audience and thread taken from the task record; no projection after signing) and signs it. Our bridge verifies the signature, grants and freshness, admits, and carries the bytes **unchanged** into the carrier under its own per-worker carrier account — a distinct, audited authority recorded in the schema.
- **Delivery.** Our bridge admits a message (signature, grant, decision guard, fences) and sends the advisory `mailbox.notify`. The donor bridge pulls `mailbox.read` from its cursor and runs its **own admission** (verification record present, addressee = this worker, unexpired, not fenced or revoked, delivery mode allowed). An admitted **task** enters the harness through the session-input adapter, not through a tool the model must call; ordinary data goes through `mailbox_read` when the policy offers it. Durable cursors on both sides advance only after a write to disk; after a reconnect: catch-up and dedup by message id; `mailbox.applied` acknowledges application, separately from the transport reply.
- **Offline.** Project mail stays durable; the donor bridge pauses the turn loop; the running turn reaches its deadline, its tool calls fail with a retryable `channel_down`, and its result waits in a durable queue; after a grace period the supervisor parks the session. The donor receives carrier credentials in no state.

### 7.8 Lifecycle

States: `enrolled → active ⇄ stopped (donor) | suspended (project) → retired → revoked → purged`. Donor: `stop` (persist the mark first, then end the harness processes; bridge and keys stay), `leave` (close the channel, report `retire`, keep keys and configuration; `init --rejoin` returns the same identity to a new workplace), `purge --confirm` (delete keys, configuration and home; the helper removes both accounts, firewall, sandbox and daemon; prints the revocation outcome or "channel unreachable; the project must revoke separately" — a lost channel is not proof of revocation). Project: `suspend` (grants paused, sessions closed), `retire` (grants and channel authorisation revoked, sessions closed, jobs and descendants killed and verified gone, key removed, the home deleted rather than archived — only a narrow service-generated metadata export is kept (review F-1, accepted) — account released; the identity stays pinned), `revoke` (root-signed revocation of the keys; a return needs a new key through a new enrolment). Stop and revocation marks are written before any service restart; removing an SSH key never substitutes for closing established sessions.

### 7.9 Order

**Slice 0 first**: a single-host MVP with separate OS identities for the key keeper, the broker and the worker on our host, then any donor. **A remote workplace requires enforced networking:** it is admissible on a host only after the user manager's v1 firewall (broker slice 2) runs there (F-19), whichever donor variant comes first. Freelance marketplace (assessed, after the single-host MVP and the two-domain federation test): a Space on a separate carrier server with signed cards `swarma-agent-card/1`, offers `swarma-offer/1` and acceptances `swarma-accept/1` that end in an ordinary invitation; reputation as signed receipts `swarma-receipt/1` from project roots; invite-only entry; only public task projections; payment outside the system. It relaxes none of the remote-worker constraints.

## 8. Provider credentials

- **Facts.** No vendor offers short-lived subscription leases; subscription logins are single-use-rotating refresh-token families, so shared copies self-destruct on concurrent refresh. Vendor terms bind subscriptions to one person and ordinary individual use. Claude: `claude setup-token` runs the ordinary browser login and prints a one-year access token without storing it; `CLAUDE_CODE_OAUTH_TOKEN` wins over the keychain for the whole session; it cannot be shortened, narrowed or refreshed in place; revocation only in the claude.ai interface; `--bare` never reads OAuth; whether the keychain stays untouched while the token is in the environment is a planned measurement, not yet measured. Codex: `auth.json` is rewritten in place and rotates; **measured by `rwh`**: several app-servers sharing one file race on refresh (eight callers: one refresh with its lock, eight without); keyring per `CODEX_HOME` is a source reading, the live probe is pending. Muse: `META_API_KEY` always wins.
- **First implementation (decided posture, 2026-10-07).** Subscriptions now, tokens architecturally; Team and Business not in release 1; one person = one subscription; no traffic interception (credential injection at the egress proxy stays research only, providers may flag intercepted traffic). Agents hold credentials in this phase (assurance mode T): a token in the harness environment **can** be read by the harness; non-extractability is a separate later design.
- **Auth nodes** (CIP-0010, proposed): a record `auth/<label>/` per OS user, harness and account, holding only references and metadata (kind such as `claude-oauth-token`, `codex-auth-owner`, `codex-access-token`, `meta-api-key`; a reference to the protected store; enrolled at; issued at *if reported*; expires at or "unknown"; last failure). The material lives in the user's protected store (the login keychain for interactive users; on a donor per the variant table of §7.2: Secure Enclave or 0600 files, no Keychain in B). The root node has the label `root`. Crossing OS users goes through the credential broker.
- **Inherited-auth homes**: a separate axis `credential_source.<profile>.<harness>` = `per-home` (default) | `node:<label>` | `helper`, in the *user* configuration layer; a system lock never selects it; a package may state a non-authoritative requirement but never name a node. A home with a node source holds no credentials of its own; the executor injects: Claude via `CLAUDE_CODE_OAUTH_TOKEN` (no keychain entry, no `.credentials.json`; never with `--bare`); Codex personal plan via a **single auth owner** per account (`curator env credential owner`, the only refresher, holding a lock on the native `auth.json`) that hands launches external access tokens through the app-server, so launches hold no `auth.json` and run with `ephemeral` storage; Codex Business via `CODEX_ACCESS_TOKEN`; Muse via `META_API_KEY`. Missing, unreadable or conflicting sources refuse (`credential_node_missing`, `credential_source_conflict`, `environment_credential_conflict`) with no fallback; a keyring-backed native Codex login is refused until a human switches it to `file`. This supersedes "one shared `auth.json` per account".
- **Gates for tracked and headless launches**: the plan carries the mandatory extension `works.relux.curator.credential/1`; admission refuses (`credential_injection_unavailable`) unless the executor declared `credential-injection/1` (agent-side `curator-run`, later the SH2+ `swarma-session-runner` sharing its launch library, and the donor-side remote-worker supervisor). The session-host service and board runner have no credential lookup or broker client (D-EXECUTOR; credential broker §3.1, session host §3.2). The capability is necessary, not sufficient: after the agent UID transition and on a fresh broker connection, the local executor re-resolves the **protected binding** `credential_binding/1` from its trusted store (executor identity, profile, harness, account label, channel, provider address, approved binary digest, policy generation); a caller's `source_ref` never replaces it. Variable names are reserved, conflicting sources refuse instead of "the higher priority wins", and the harness environment is separated from the MCP children's environment. Behind the capability stands a qualification on lab runners.
- **Status and events**: `env status` prints node, kind, enrolled, issued (reported) and expiry (computed or unknown); events `credential_expiring`, `credential_expired`, `credential_error {class: auth | permission | quota | unknown}` (honestly `unknown` where a 401/403 cannot be told apart), `reauth_required`. Reaction: park, notify, no endless retries; recovery per persistence mode (Claude resumes its transcript, Codex `ephemeral` restarts from the task snapshot, Muse from its session log) — each a lab measurement. Tracked and headless launches use only modes without an interactive `/login`.
- **Remote workers**: the machine owner enrols the node at `init` under the **bridge identity**; the supervisor is an executor with the capability and takes the binding from the bridge's store; the harness starts locked with the token in its environment only. Our side holds none of the donor's credentials.
- **CIP-0003**: accepted narrowed together with CIP-0010 in one decision (decided 2026-10-10): `per-home`, the opaque-`source_ref` token mode (as the node mode with the gates above), `helper` for API keys, precedence rules, the protected-store read order with no fallback, Linux legacy handling, migration and its item 5 (as `credential_injection_unavailable`, lifted per executor) stay; `shared-file` is replaced by nodes; the claim that a file cannot be shared at all on macOS is dropped; Decision 0017 Q7 (no stripped copies) unchanged.
- **Order: slice 0 first** — a minimal broker interface: `credential_binding/1` over a Unix socket with peer credentials, from the operator's user to an executor under another OS user, proven end to end (foreign caller, foreign account, expired binding refuse) before nodes are generalised and before any donor. P1 after Curator v0.15.0-rc.5. Not here: the full broker (leases, concurrency within one person's scope), proxy injection, Team/Enterprise, `CLAUDE_CODE_OAUTH_REFRESH_TOKEN`.
- **Decided 2026-10-10 (CIP-0010 revision 2.2)**: a launch whose credential source is not configured keeps `per-home` in version 1 (today's behaviour); **version 2 refuses** it, and the migration writes `per-home` explicitly for every existing home that already holds a login («если вдруг c - правильнее - то просто пишем потом в спеку к v2»); CIP-0003 is adopted narrowed as part of CIP-0010. **Still open**: Codex personal plan through the single owner with a race test on 0.159.0 as the condition; Muse only as `meta-api-key`; slice 0 as the first item after rc.5. Still open from v1.3: who owns re-login after a logout (proposal: the host notices and parks, the broker runs the vendor's own flow and relays the code to the account owner's phone, the host restarts on the broker's signal).

## 9. Session-host duties added on 2026-10-08

- **Input hygiene across restarts.** Claude Code's queued-prompt records and drafts are restored on `--resume` and a remote-control client may show an old prompt in its input box; tooling that types into panes can leave residue. The host checks for unmatched queued items before parking, shows them to the operator, and after a restart reminds the operator to clear the client input. (decided; today in the relaunch script)
- **Auto-answers.** The wrapper answers harness security prompts only from an allowlist under the parent's `session.approve`; everything else parks and asks a holder of that grant (a parent orchestrator or a human). Every auto-answer is audited.
