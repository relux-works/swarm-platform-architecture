# Contract: trust and isolation — identities, keys, grants, workplaces, channels, credentials

Status: VISION v1.3 contract draft (2026-10-08). Collects the owners' call of 2026-10-07, the design sessions of 2026-10-06…08 and Curator's remote-worker CIPs 0008–0010 revision 2 (§7, §8). Russian narrative with the same content: wiki `session-host/architecture.ru.md` §7. Diagrams: `diagrams/plantuml/sequence/` (`keeper-sign`, `grant-issue-and-check`, `action-namespace-registration`, `delegated-action-handler`, `mailbox-delivery`, `spawn-with-user`, `keeper-team-start`, `external-agent-onboarding`, `remote-workplace-attach`, `remote-worker-join-handshake`, `remote-worker-retire`). Status marks: **decided** (owners), **proposed** (this draft), **open**.

## 1. Principles

1. **An agent never holds a secret.** It asks a privileged neighbour to do something with the secret. What an agent cannot do physically, a prompt injection cannot make it do.
2. **Trust never rests on the transport.** Pipes are encrypted as hygiene; authority is only a signature over exact bytes plus a grant. Where a command came from does not matter.
3. **The kernel is the sandbox.** One OS user per autonomous agent; the kernel's user isolation, not a container or a prompt, is the boundary. (decided)
4. **Checks happen where the action happens**, never in the requester. One verification library everywhere.
5. **No free text in the authority layer.** Actions are registered names with schemas; free text reaches agents only as `data` or a doorbell.

## 2. Identities and the key keeper

- **Identity** = a stable derivation path plus its public key, never an OS path or UID: `purpose'/product'/project'/agent'` (hardened derivation, BIP-32/SLIP-0010; a child key reveals nothing about its siblings). (decided)
- **Root.** The keeper publishes the public root; the owner confirms it once at installation. Each agent identity is a public key plus the root's signature "descendant N". Anyone verifies the chain offline.
- **Keeper** (privileged daemon, the only holder of the master secret in Secure Enclave / TPM / DPAPI-CNG where available; on macOS a LaunchDaemon with the System keychain). Unix socket API: `sign(bytes)`, `decrypt(blob)`, `pubkey(identity)`, `register(uid, path)` (dispatcher only), `revoke(identity)` (owner act or dispatcher at retire). The kernel reports the caller's UID (`LOCAL_PEERCRED` / `SO_PEERCRED`); the keeper keeps a mutable map *UID → path* and answers only with that identity's key. No API returns a private key; key pairs are never placed in an agent's keychain.
- **Decrypt** returns plaintext only to the calling process, audited and rate-limited. The keeper protects the key, not the plaintext: packages are addressed only to whoever must read them and carry nothing extra.
- **Lifecycle.** Deleting the OS user stops the agent; re-registering the same path on another machine with the same master secret restores the identity (migration). Retiring = a root-signed revocation record.
- **External identities** (other organisations, remote workers) bring their own key pair: a self-signed certificate is verified, the public key is pinned, and the root signs an admission record "external key K admitted with role R". Both kinds live in one registry under the same checks.
- **Risk.** Master-secret compromise compromises everyone: the keeper stays minimal, privileged, audited.

## 3. Grants

- **Record.** `grant/1 {issuer, subject (key or role), actions[], targets[], conditions{lang, …}, delegable{depth}, parent?, expires_at, sig}`. Role bindings are separate signed records, so a grant to a role covers whoever holds it; playbook role rights are grants to roles.
- **Delegation with attenuation.** A requester may grant at most a subset of what it holds and of what is marked delegable: subset of actions and targets, expiry not later, depth not deeper; `parent` links the chain to the root. The dispatcher refuses a spawn whose requested child grants exceed the requester's delegable grants. Inspiration: SPKI/SDSI, Macaroons, UCAN, Biscuit (Biscuit's Datalog and offline verification are a candidate implementation). (proposed)
- **Conditions and the policy language.** `conditions.lang = caveats/v1` today (time windows, counters, operator confirmation, target lists); `datalog/v1` or similar later. One library with pluggable evaluators; envelopes carry only grant references, so a policy language never changes wire formats. (proposed)
- **Checking.** The task core checks role grants when it moves a task or accepts a result; the dispatcher checks spawn grants; the broker checks "may write to this agent" before delivery; the bridge checks the audience on the way out. An orchestrator asks; it never judges.
- **Issuing and syncing.** Grants are managed in the owner's client app and synced through a signed trust gateway into the registry; services subscribe to revocation snapshots and re-admit at dispatch. Where the registry lives (git journal, Matrix state, a service, a hybrid) is **open**.

## 4. The action vocabulary and handlers

- **Vocabulary.** A registered set of namespaces, each with argument schemas and a handler: platform base `session.*`, `goal.*`, `board.*`, `user.*`, `spawn.*`, `post`, `inbox`, `terminal.raw`; later e.g. `github-runner.*`. Targets are typed resource ids (`session:…`, `host:mini/runners/x`, rooms, board elements); wildcards only in grants, commands name a concrete target.
- **Registration** (three signed records):
  1. `handler-manifest/1 {handler identity, actions{name: args schema}, target form, effects: reversible|irreversible, sig}` published by the handler;
  2. `action-namespace/1 {namespace, handler, manifest_sha256, hosts[], grantable_by[], issued_by (chain), expires_at, sig}` issued by the owner or by an agent holding `registry.actions.register` — attenuated, e.g. only inside `ops.*`; the same name again only with the same handler or a root-signed replacement; removal is a revocation;
  3. grants and commands name the registered action. A grant on an unregistered action is refused at issue; the gate validates arguments against the manifest.
- **Handlers.** A *process* handler (deterministic helper) for OS-level and irreversible effects re-verifies the chain itself, executes exactly one registered operation, audits and signs its receipt. An *agent* handler (e.g. an admin orchestrator with wide grants) receives a typed `authoritative` item with a verification record, may re-verify, adds judgement, and executes with its own permissions (a narrow sudo rule or the helper); it cannot amplify. `effects: irreversible` hints that a process must handle it.
- **Worked example.** G1: root → Alexis's pinned key, `github-runner.{restart,stop}` over `host:mini/runners/*`, caveats (hours, rate), delegable depth 1. G2: Alexis → his orchestrator, a subset, `parent: G1`. His orchestrator sends `swarm-envelope/2 {action github-runner.restart, args{runner x}, target host:mini/runners/x, grant_refs [G2, G1]}` signed by its keeper. Our gate verifies signature, pin, chain, attenuation, schema, caveats, revocation; the registry names the handler; a receipt returns signed. Sequences `action-namespace-registration`, `delegated-action-handler`.

## 5. Agent workplaces (one OS user per agent)

- **Every autonomous agent** — meta-keeper, keepers, orchestrators, standing specialists, ephemeral workers, remote workers' workplaces — runs as its own OS user. (decided)
- **Creation** by one narrow privileged helper that sudoers admits for the dispatcher (and nothing else); the helper creates the user, home, group, ACL, quotas and firewall rules, and removes them at retire. A system-administrator *capability* is a grant (`user.create`), not an agent.
- **Network.** The kernel firewall per UID (pf `user`, nftables owner match, WFP) admits only the message broker and the egress proxy of the network profile; everything else is dropped and counted. This makes network profiles enforced rather than cooperative.
- **Homes.** Flat (`/Users/agents/<id>`): orchestrator home 0700; worker home 0750 plus an inherited ACL read entry for the parent (macOS `chmod +a "orch allow list,search,read,…,file_inherit,directory_inherit"`, Linux `setfacl -R -m u:orch:rX` and the default ACL). Limits: on Linux the ACL mask follows the file mode (a 0600 file stays unreadable); on macOS the owner can remove the ACL. ACL is a convenience; guaranteed observability comes from the host (journal, transcripts) and from board results and handoff packages.
- **Ephemeral trees.** A "cheap tree copy" abstraction: APFS clone on macOS, `cp --reflink=auto` on Btrfs/XFS (a plain copy on ext4), overlayfs optional; default everywhere `git worktree`, which works out of the box on Debian and Arch. Session logs stay out of git.
- **Stable team.** A project binding declares `team[] {role, identity, standing|ephemeral, max}`; S4 `up` brings standing members back idempotently after a reboot; ephemeral users are created per run and removed at retire.
- **Privilege model.**

| Component | Runs as | Why |
|---|---|---|
| keeper | root (LaunchDaemon / service) | hardware-backed secret; peer-UID signing |
| user/firewall helper | root for one command (sudoers) | users, ACL, pf/nftables rules |
| session host | own unprivileged user | starts holders as agents through the helper |
| bridge and broker | own unprivileged user | holds carrier credentials; peer-UID sockets |
| dispatcher | own unprivileged user | accounting; calls the helper |
| agents | one user each | kernel boundary |
| human administrator | own account | runs nothing of the platform |

## 6. Entry channels and the message path

- **Three entries.** *Root channel*: the operator only, locally — a signed command or a terminal under the exclusive lease (`terminal.raw`); the host writes straight into the PTY. *External channel*: carrier plus broker — the only path for every external party, external orchestrators included; never the root channel. *Join point*: a one-time HTTPS endpoint for introductions (certificates in, credential packages out), never commands; unnecessary when the package travels out of band. (decided)
- **Agents never read the carrier.** The broker (the room member) holds carrier credentials. A provider persists each raw event (append, fsync) *before* advancing its carrier cursor, then hands the bridge an envelope; a replay after a crash is harmless because admission is idempotent per (sender, id).
- **Trust gate**, pure library, no network, no model: canonicalise (JCS) → find the key by `key_id` in the registry snapshot → verify Ed25519 → derive the sender → load `grant_refs` and walk the chain to the root (each link signed by its issuer, subject = next issuer, actions/targets narrowing, expiries nested) → revocation snapshot → time window and replay journal → target binding revision → verdict and an admission record signed by the bridge. Any failure is `reject` with a reason and an audit line.
- **Decision guard.** After the gate, a small local model compares the request with the addressee's grant specification and injection patterns and records `{body hash, sender, grants used, model version, verdict, fingerprint}`; the host rings the doorbell; the agent fetches body plus verification record from the **Mailbox** (`inbox read`, In and Out) and may re-verify. If the guard is unavailable, the answer is no.
- **Who may write In / read Out.** By default only the parent (granted automatically at spawn); everyone else through the broker. The owner, as root of trust, holds every grant. **Proposed.**
- **Encryption.** Signatures over the carrier's own end-to-end encryption; no envelope encryption of our own for now. People use ordinary clients; signatures ride in event metadata. (decided)
- **Federation test.** The owners' two-domain setup (own Matrix servers, machines, regions; shared rooms for shared projects) is the reference test for federation and onboarding after the single-host MVP.

## 7. Remote workplaces

Detailed by Curator's CIP-0008 (lockdown launch mode), CIP-0009 (donor-side deployment and bridge) and CIP-0010 (credentials), revision 2 after the architecture review of 2026-10-08 (curator-spec PR #134 at `5100b46`, draft). Everything in §7.2–§7.9 is **proposed** unless marked; points waiting for the owners' answers are listed in §7.10.

### 7.1 Shape (decided)

A remote worker's harness runs on the **donor** machine and does all its work on our host. On our host it gets a workplace user; one SSH connection goes from the donor towards our host and carries tool execution and the mailbox; our host never opens connections to, or sends commands into, the donor machine. Remote workers use their own provider credentials; ours never reach the donor, and the donor never receives carrier credentials.

### 7.2 The donor machine: two OS identities

- **Untrusted harness identity** `swarma-rw-<project>`: the harness in lockdown (§7.3) plus the stdio relay `swarma-remote-tools`, which holds no keys and has no network; home 0700, no login, quotas; owns only its managed home and scratch directory.
- **Trusted bridge identity** `swarma-rb-<project>`: keys, locked configuration, audit, cursors. The bridge service runs as a `launchd` system daemon (survives logout, needs no login keychain): it holds the single SSH connection, serves the relay over a Unix socket that checks peer credentials, signs outgoing envelopes, admits incoming items, keeps the budget counters (the trusted side's counters are authoritative) and executes `stop`. The supervisor `curator remote-worker run` is part of it and starts the harness **as the harness identity**.
- One identity for both was rejected by the review: with a shared UID the per-UID firewall distinguishes nothing, and a shared home exposes audit, state and keys.
- **Privileged helper** `swarma-helper`: root for one command (sudoers on this absolute path only) with a closed operation schema (`create-worker`, `remove-worker`, `set-egress`, `apply-sandbox`, `rollback`); it allocates accounts and IDs itself, takes only a project label, uses fixed templates, journals every step and rolls back; it never removes a pre-existing account.
- **Egress by UID** (`pf` anchor): the harness reaches only the local provider proxy (an allowlist of provider hosts per qualified tuple); the bridge reaches only our SSH host and the join point; nothing inbound.
- **Sandbox**: a Seatbelt profile for the harness process with an explicit allowlist (read and execute the protected binary root and runtime libraries, read/write the managed home and scratch, connect to the relay socket and the proxy port); everything else denied. The **read boundary is mandatory**: it neutralises read-only tools that a harness cannot remove (Muse) and keeps the bridge home closed even if file modes were wrong. The profile revision is part of the tuple and the plan.
- **Protected binary root** `/opt/swarma/<release>/`, root-owned, read-only, no writable parent; the bridge starts every binary by absolute path and checks its digest against the release manifest. The MCP pin covers the relay's declaration; the binaries are pinned separately.
- **Transactional install**: a journal per step and `rollback` in reverse order; an interrupted install never leaves a weakened rule.
- **Keys** in release 1: 0600 files of the bridge identity (a daemon without a login session cannot use the login keychain); non-exportable keys are a later hardening.
- **Platforms**: macOS first (what `rwh` measured); Linux next (two system users, `nftables` by UID, `systemd` service, harness via `systemd-run --uid` with `NoNewPrivileges`, a cgroup for lifetime, **Landlock** as the read boundary); Windows no. An unsupported host is refused at `init`.
- **Negative tests on real inputs** (`init`, launch, tool call, stop): reads outside the allowlist, egress outside it, the proxy refusing a foreign host, the socket refusing a foreign UID, the helper refusing a repeated label, a symlink in a path, an arbitrary user name in `remove-worker`, argument injection; an install interrupted midway rolls back.

### 7.3 Lockdown launch mode (CIP-0008)

- **Tool posture** `tool_posture.<profile>` = `open | lockdown`, a *machine* setting the donor locks in system configuration. The lock rule is amended: a lock may fix exactly the pair `lockdown` + `remote-auto` (a lock still never selects credentials).
- **Permissions `remote-auto`** ("marked yolo"): the relay's tools are pre-approved, everything else that would ask is denied silently, and no native bypass appears in any source (flags, settings file, configuration key); its presence alone is a refusal. Allowed only with `lockdown`; each harness has a headless and an interactive spelling, each with its own test.
- **Qualified tuples** instead of "version ≥ x": exact version, binary digest, platform, transport, model, settings policy, sandbox revision; any update is a requalification; a tuple without a row is refused. Rows today: Claude Code 2.1.293 (`--restricted --tools "" --strict-mcp-config --mcp-config <protected> --settings <protected> --setting-sources "" --disable-slash-commands`, protected files owned by the bridge identity, the system managed policy read and refused if it enables bypass, MCP or hooks, empty cwd, never `--bare` because it does not read OAuth); Codex 0.159.0 over **app-server only** (managed `config.toml` as base configuration, `sandbox_mode = read-only`, approvals routed to the supervisor and refused, web search, analytics, hooks, plugins and 23 feature switches off, empty tool list, pruned model catalogue, pinned model, `--strict-config`; `codex exec` only after its own qualification); Muse 1.4.3 on macOS only (`--disable-shell --disable-write --disable-web-tools --no-foreign-personal-context`, session logs kept under quota as untrusted data; read tools cannot be removed, so the OS read boundary is mandatory; donors with Muse are a second wave). Updaters, telemetry, logs, settings, hosted tools and instruction discovery are inventoried per tuple; telemetry and updates are bounded by the UID egress allowlist, not by flags.
- **Launcher grammar**: the *generated policy* (written by agents-management) is mandatory, and a plan where a member is missing, duplicated, aliased or set from another source is refused at admission; the *caller tail* after `--` is parsed against a closed per-harness allowlist (Claude: `--output-format`, `--verbose`, `--resume`, `--session-id`, `--max-turns`; Codex app-server: nothing). Errors: `tool_posture_conflict`, `tool_posture_unknown_argument`; an unknown harness or tuple is refused.
- **Plan and policy generation**: the posture is a mandatory plan extension (an admission that does not know it refuses); the machine configuration keeps a policy-generation counter that the composer copies into the plan and the final executor re-reads at launch and at every resume, refusing on mismatch; changing `tool_posture` or the permissions stops a live session at once. A donor supervisor's statement about its kernel is a statement, not an attestation, and is recorded as such.
- **No second compiler**: agents-management composes through the single construction site; the remote-worker supervisor only consumes the composed plan, like the session host. Amendments to Decisions 0019/0021 are needed before implementation.
- **What the donor sees and can do**, locally and without us: `curator env status` (posture, tuple, generation, permissions with an honest sentence, relay, project); an audit line per tool call written by the bridge identity (name, argument hash, sizes, time, no content); `stop`, `leave`, `purge`.
- **Honest banner**: "no local tool is offered to the model; the harness runtime keeps its managed state; tools execute in the project's workplace" — not "nothing can be done on this machine".
- **Layers, strongest first**: two OS identities, kernel sandbox and UID egress on the donor; no local tool offered to the model; launcher grammar and admission checks; the executor's tripwire and audit (detection after dispatch); the workplace policy on our host.

### 7.4 Join (CIP-0009)

1. **Invitation** `swarma-invitation/1`: id, join point, root fingerprint, SSH host-key fingerprint, project, role, expiry, and a one-use random code of at least 128 bits (a short-lived bootstrap secret), delivered over a second channel.
2. `curator remote-worker init <invitation>` refuses an unsupported host, calls the helper, and the bridge identity generates **three role-separated keys**: `K_sig` (Ed25519, signing), `K_enc` (X25519, package decryption), `K_ssh` (SSH). An enrolment certificate over the three keys, name, role, invitation id and expiry is self-signed by `K_sig`; its fingerprint is shown. (Supersedes the single key pair and `swarma join` of the v1.3 text; the command name is open, §7.10.)
3. **Server challenge**: `POST /join/challenge` returns a challenge bound to the invitation (5 minutes, attempt counter). **DNS cross-check** through a trusted validator only: TXT `_swarma`, SSHFP and TLSA must be *secure* and equal to the invitation; *bogus* refuses; *indeterminate* (no validator) proceeds on the pinned fingerprints and records it. No step downgrades on failure.
4. **Transcript** `swarma-join/1` (deterministic CBOR, domain-separated: version, invitation id, project, role, three keys, server challenge, client nonce, expiry, algorithms), signed by `K_sig` and posted with the code over TLS pinned to the join point's certificate. The join point checks the code in constant time, the signature, the challenge binding and the expiry, **consumes the invitation atomically** (a tombstone per invitation id: a retry with the same `K_sig` returns the same pending enrolment, another key is refused), rate-limits, and accepts only three verbs (challenge, cert, collect).
5. **Human check and admission**: the operator reads the fingerprint back over the second channel, pins the three keys, the root signs the admission, grants are issued. The **package** `swarma-credential-package/1` (root key, operator certificate signed by the root with scope `onboard`, host, SSH host key, workplace user, binding digest, qualified tuple, policy generation, expiry) is encrypted to `K_enc` (X25519 + HKDF + ChaCha20-Poly1305, transcript digest as associated data) and signed by the operator certificate. It carries **no carrier identity and no tokens** (supersedes the v1.3 text).
6. **Collect** with a second challenge signed by `K_sig`; the bridge decrypts, verifies the operator certificate against the pinned root, the package signature and the associated data, writes the locked configuration and binding, installs the relay declaration, and reports "registered, waiting for tasks".
7. The dispatcher provisions the workplace on our host (§7.5).

### 7.5 The bridge protocol `swarma-rb/1` and our SSH side

- **SSH**: one connection from the donor bridge under the workplace user with `K_ssh`; our host key is checked against the pin (and SSHFP when secure) on **every** connection; no trust on first use. Our `sshd` has a `Match` block for workplace users: a **root-owned authorized-keys file outside the user's home** (a shell tool cannot append a key), `restrict` and a forced command by absolute path, `PermitUserRC no`, `PermitUserEnvironment no`, no agent, port or X11 forwarding, no PTY.
- **Frames**: a 4-byte length checked **before** allocation (maximum 1 MiB), deterministic CBOR without duplicate keys, `hello` with versions, request ids scoped to the connection, and a client **`op_key`** for idempotency: the server caches results by `op_key` for ten minutes, so a reconnect after a lost reply returns the cached result or `unknown_result` and never repeats an effect.
- **Methods**: `exec`, `cancel`, `stdin`, file operations, `mailbox.read`, `mailbox.post`, `mailbox.applied`; from the server `mailbox.notify` (advisory) and `policy.changed`. **The server's policy is authoritative**: timeouts, output ceilings and leases can only be lowered; `cancel` and `stdin` apply only to the caller's live job; every method is authorised by the policy; flow-control credits; environment variables only from `env_allow`.
- **Job lifetime**: every `exec` runs in its own process group (plus a cgroup on Linux) under a lease; lease expiry, `cancel` or a transport drop after a grace period kills the group and verifies that no descendant remains — a test, not an assumption.

### 7.6 Workplace backend contract `swarma-workplace-exec/1`

The first backend is the workplace as an OS user (§5). The contract lists what any backend must give: an execution API with ceilings; a per-worker policy (tools, write scope, network, limits, `env_allow`) whose id appears on every audit line; the tool-set intersection; audit on our side; review and export of changes as a patch; cleanup. The maximum tool set is `bash`, `read_file`, `write_file`, `apply_patch`, `mailbox_read`, `mailbox_post`; the **effective** set is its intersection with the workplace policy (a read-only worker gets `read_file` and nothing else). No `enrol`, `key` or `config` tools. A container backend joins through an adapter only after its own qualification; its guarantees are not borrowed.

### 7.7 Signing and delivery

- **Signing on the donor side.** `K_sig` never leaves the donor's bridge identity. The donor bridge builds the **final** envelope (canonical bytes with audience and thread taken from the task record; no projection after signing) and signs it. Our bridge verifies the signature, grants and freshness, admits, and carries the bytes **unchanged** into the carrier under its own per-worker carrier account — a distinct, audited authority recorded in the schema.
- **Delivery.** Our bridge admits a message (signature, grant, decision guard, fences) and sends the advisory `mailbox.notify`. The donor bridge pulls `mailbox.read` from its cursor and runs its **own admission** (verification record present, addressee = this worker, unexpired, not fenced or revoked, delivery mode allowed). An admitted **task** enters the harness through the session-input adapter, not through a tool the model must call; ordinary data goes through `mailbox_read` when the policy offers it. Durable cursors on both sides advance only after a write to disk; after a reconnect: catch-up and dedup by message id; `mailbox.applied` acknowledges application, separately from the transport reply.
- **Offline.** Project mail stays durable; the donor bridge pauses the turn loop; the running turn reaches its deadline, its tool calls fail with a retryable `channel_down`, and its result waits in a durable queue; after a grace period the supervisor parks the session. The donor receives carrier credentials in no state.

### 7.8 Lifecycle

States: `enrolled → active ⇄ stopped (donor) | suspended (project) → retired → revoked → purged`. Donor: `stop` (persist the mark first, then end the harness processes; bridge and keys stay), `leave` (close the channel, report `retire`, keep keys and configuration; `init --rejoin` returns the same identity to a new workplace), `purge --confirm` (delete keys, configuration and home; the helper removes both accounts, firewall, sandbox and daemon; prints the revocation outcome or "channel unreachable; the project must revoke separately" — a lost channel is not proof of revocation). Project: `suspend` (grants paused, sessions closed), `retire` (grants and channel authorisation revoked, sessions closed, jobs and descendants killed and verified gone, key removed, only non-credential artifacts archived, account released; the identity stays pinned), `revoke` (root-signed revocation of the keys; a return needs a new key through a new enrolment). Stop and revocation marks are written before any service restart; removing an SSH key never substitutes for closing established sessions.

### 7.9 Order

**Slice 0 first**: a single-host MVP with separate OS identities for the key keeper, the broker and the worker on our host, then any donor. Freelance marketplace (assessed, after the single-host MVP and the two-domain federation test): a Space on a separate carrier server with signed cards `swarma-agent-card/1`, offers `swarma-offer/1` and acceptances `swarma-accept/1` that end in an ordinary invitation; reputation as signed receipts `swarma-receipt/1` from project roots; invite-only entry; only public task projections; payment outside the system. It relaxes none of the remote-worker constraints.

## 8. Provider credentials

- **Facts.** No vendor offers short-lived subscription leases; subscription logins are single-use-rotating refresh-token families, so shared copies self-destruct on concurrent refresh. Vendor terms bind subscriptions to one person and ordinary individual use. Claude: `claude setup-token` runs the ordinary browser login and prints a one-year access token without storing it; `CLAUDE_CODE_OAUTH_TOKEN` wins over the keychain for the whole session; it cannot be shortened, narrowed or refreshed in place; revocation only in the claude.ai interface; `--bare` never reads OAuth; whether the keychain stays untouched while the token is in the environment is a planned measurement, not yet measured. Codex: `auth.json` is rewritten in place and rotates; **measured by `rwh`**: several app-servers sharing one file race on refresh (eight callers: one refresh with its lock, eight without); keyring per `CODEX_HOME` is a source reading, the live probe is pending. Muse: `META_API_KEY` always wins.
- **First implementation (decided posture, 2026-10-07).** Subscriptions now, tokens architecturally; Team and Business not in release 1; one person = one subscription; no traffic interception (credential injection at the egress proxy stays research only, providers may flag intercepted traffic). Agents hold credentials in this phase (assurance mode T): a token in the harness environment **can** be read by the harness; non-extractability is a separate later design.
- **Auth nodes** (CIP-0010, proposed): a record `auth/<label>/` per OS user, harness and account, holding only references and metadata (kind such as `claude-oauth-token`, `codex-auth-owner`, `codex-access-token`, `meta-api-key`; a reference to the protected store; enrolled at; issued at *if reported*; expires at or "unknown"; last failure). The material lives in the user's protected store (the login keychain for interactive users, a 0600 file for service identities such as the donor bridge). The root node has the label `root`. Crossing OS users goes through the credential broker.
- **Inherited-auth homes**: a separate axis `credential_source.<profile>.<harness>` = `per-home` (default) | `node:<label>` | `helper`, in the *user* configuration layer; a system lock never selects it; a package may state a non-authoritative requirement but never name a node. A home with a node source holds no credentials of its own; the executor injects: Claude via `CLAUDE_CODE_OAUTH_TOKEN` (no keychain entry, no `.credentials.json`; never with `--bare`); Codex personal plan via a **single auth owner** per account (`curator env credential owner`, the only refresher, holding a lock on the native `auth.json`) that hands launches external access tokens through the app-server, so launches hold no `auth.json` and run with `ephemeral` storage; Codex Business via `CODEX_ACCESS_TOKEN`; Muse via `META_API_KEY`. Missing, unreadable or conflicting sources refuse (`credential_node_missing`, `credential_source_conflict`, `environment_credential_conflict`) with no fallback; a keyring-backed native Codex login is refused until a human switches it to `file`. This supersedes "one shared `auth.json` per account".
- **Gates for tracked and headless launches**: the plan carries the mandatory extension `works.relux.curator.credential/1`; admission refuses (`credential_injection_unavailable`) unless the executor declared `credential-injection/1` (session host, `task-board spawn` runner, remote-worker supervisor). The capability is necessary, not sufficient: at launch the executor re-resolves the **protected binding** `credential_binding/1` from its trusted store (executor identity, profile, harness, account label, channel, provider address, approved binary digest, policy generation); a caller's `source_ref` never replaces it. Variable names are reserved, conflicting sources refuse instead of "the higher priority wins", and the harness environment is separated from the MCP children's environment. Behind the capability stands a qualification on lab runners.
- **Status and events**: `env status` prints node, kind, enrolled, issued (reported) and expiry (computed or unknown); events `credential_expiring`, `credential_expired`, `credential_error {class: auth | permission | quota | unknown}` (honestly `unknown` where a 401/403 cannot be told apart), `reauth_required`. Reaction: park, notify, no endless retries; recovery per persistence mode (Claude resumes its transcript, Codex `ephemeral` restarts from the task snapshot, Muse from its session log) — each a lab measurement. Tracked and headless launches use only modes without an interactive `/login`.
- **Remote workers**: the machine owner enrols the node at `init` under the **bridge identity**; the supervisor is an executor with the capability and takes the binding from the bridge's store; the harness starts locked with the token in its environment only. Our side holds none of the donor's credentials.
- **CIP-0003**: accepted narrowed together with CIP-0010 in one decision (proposed): `per-home`, the opaque-`source_ref` token mode (as the node mode with the gates above), `helper` for API keys, precedence rules, the protected-store read order with no fallback, Linux legacy handling, migration and its item 5 (as `credential_injection_unavailable`, lifted per executor) stay; `shared-file` is replaced by nodes; the claim that a file cannot be shared at all on macOS is dropped; Decision 0017 Q7 (no stripped copies) unchanged.
- **Order: slice 0 first** — a minimal broker interface: `credential_binding/1` over a Unix socket with peer credentials, from the operator's user to an executor under another OS user, proven end to end (foreign caller, foreign account, expired binding refuse) before nodes are generalised and before any donor. P1 after Curator v0.15.0-rc.5. Not here: the full broker (leases, concurrency within one person's scope), proxy injection, Team/Enterprise, `CLAUDE_CODE_OAUTH_REFRESH_TOKEN`.
- **Waiting for the owners' answers (open)**: the default for tracked launches after qualification (`per-home` with an explicit setting, proposed, or `node:root` when a root node exists); Codex personal plan through the single owner with a race test on 0.159.0 as the condition; accepting CIP-0003 narrowed with CIP-0010 in one decision; Muse only as `meta-api-key`; slice 0 as the first item after rc.5. Still open from v1.3: who owns re-login after a logout (proposal: the host notices and parks, the broker runs the vendor's own flow and relays the code to the account owner's phone, the host restarts on the broker's signal).

## 9. Session-host duties added on 2026-10-08
